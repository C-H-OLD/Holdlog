# Spec Kit 개발 흐름

## 현재 설정

GitHub Spec Kit 1.1.0과 Codex 스킬을 설치했다. 기능 명세를 계속 갱신하는 Living Spec 방식을 사용한다. 프로젝트 원칙은 [constitution](../.specify/memory/constitution.md), 작업 범위와 상태는 [스펙 목록](../specs/README.md)에서 찾는다.

사용자는 “개인 기록 작성·저장·조회 개발 진행”처럼 결과를 요청하면 된다. 에이전트가 아래 단계의 관련 스킬을 읽고 적용한다. 사용자가 스킬 이름을 매번 입력할 필요는 없다. “스펙만 작성”, “검사만 진행”처럼 범위를 제한한 요청은 그 범위까지만 수행한다.

## 기능 개발

| 단계 | 설치된 스킬 | 수행할 일 |
|---|---|---|
| 명세 | `$speckit-specify` | 새로운 범위의 동작·제약·상황별 기대 결과 작성 |
| 명확화 | `$speckit-clarify` | 기존 자료로 해결되지 않는 요구사항 정리 |
| 설계 | `$speckit-plan` | 기술 명세에 따라 구조·데이터·API 계약·검증 방법 작성 |
| 추가 검토 항목 | `$speckit-checklist` | 기능의 크기와 위험에 맞춰 필요한 추가 체크리스트 생성 |
| 작업 분리 | `$speckit-tasks` | 요구사항과 연결한 작업·의존성·검사 작성 |
| 일관성 검사 | `$speckit-analyze` | 읽기 전용으로 스펙·설계·작업의 충돌·누락 보고 |
| 구현 | `$speckit-implement` | 정해진 작업 구현과 관련 검사 실행 |
| 누락 확인 | `$speckit-converge` | 실제 구현과 명세 대조. 누락이 있으면 보완 작업 후 재확인 |

이미 수행한 단계는 결과를 확인해 이어간다. 원칙은 `$speckit-constitution`으로 갱신하며 매 기능마다 다시 만들지 않는다. 작은 오류 수정은 기존 스펙의 기대 결과를 확인하고 재현·수정·관련 검증을 수행하며 새 기능 스펙을 불필요하게 만들지 않는다.

### 이슈 단위 구현 범위

역할별 이슈를 구현할 때도 같은 `spec.md`·`plan.md`·공통 계약·`tasks.md`를 기준으로 삼는다. `$speckit-implement`를 적용하기 전에 사용자 요청과 선택한 이슈에 연결된 작업 ID를 실행 범위로 명시한다. 설치 스킬의 전체 작업 실행·전체 완료 규칙은 이 요청 범위에 맞춰 적용한다. 작업 목록 전체를 실행하거나 다른 담당자의 작업을 가져오지 않는다.

전체 작업 목록에서 선행 관계를 읽되 구현·검사·체크 갱신은 선택한 작업에 한정한다. 미완료 선행 작업이 필요하면 차단 사유를 알리고, 요청 밖의 선행 작업을 임의 구현하지 않는다. 작업 목록을 일부만 남긴 사본으로 대체하거나 다른 작업을 삭제·완료 처리하지 않는다. 선택한 작업의 구현 완료와 스펙 전체 완료를 따로 보고하며, 전체 완료는 필수 작업과 최종 연동 검증을 모두 충족했을 때만 판단한다.

기본 `checklists/requirements.md`는 `$speckit-specify`·`$speckit-clarify`가 명세 품질을 확인하며 관리한다. 추가 체크리스트는 필요한 경우에만 만들고 새 항목은 미완료로 둔다. 추가 항목의 검토자는 사용자이며, 사용자가 검토를 명시적으로 맡긴 경우 에이전트가 근거를 확인하고 완료 표시를 돕는다. 생성만으로 품질 확인을 마친 것으로 취급하지 않는다. 구현 전에 미완료 항목을 확인하고 설치 스킬의 진행 조건을 따른다.

`$speckit-analyze` 실행 중에는 파일을 수정하지 않는다. 보고 후 수정은 별도 작업으로 진행한다. 사용자가 수정까지 요청한 범위라면 그 범위 안에서 고치고 다시 검사하며, 검사만 요청했다면 결과를 보고한다.

동작 변경은 기존 `spec.md`를 먼저 수정하고 관련 계획·작업·코드·검사를 갱신한다. 구현 방법만 바뀌면 계획과 작업을 고친다. 새 기능은 새 스펙과 상위 이슈를 만들고 서브 작업을 연결한다. 기존 기능 변경은 같은 스펙을 사용하고, 새 필수 작업이 생기면 기존 상위 이슈를 다시 열어 필요한 서브 작업·완료 체크·검증 범위를 갱신한다. 이미 완료된 작업의 증거는 유지한다. 중요 결정 이유만 [기록 폴더](history/README.md)에 보관한다. 파생 문서를 새로 만들기 전에 유지할 결정과 아직 하지 않은 작업을 확인한다.

## 기존 문서와 연결

- 공통 기능·권한·시간대·기록 관계·기술·UI 규칙은 기존 기준 문서를 참조한다.
- 기능 스펙으로 원본을 옮긴 범위는 기존 문서를 요약·링크로 대체한다. 같은 상세 규칙을 두곳에서 고치지 않는다.
- 기존 S·D·B·T 번호와 화면 연결을 보존한다. 기능별 FR·SC 번호는 해당 스펙 안에서 사용하고 기존 번호와 연결한다.
- 요구사항별로 구현 작업·검증 방법·결과를 연결한다. 현재 대상 범위와 실제 구현 완료 범위는 구분한다.
- 계약을 정한 뒤 독립 구현을 나누고 합친 뒤 실제 연동을 검사한다. 독립 에이전트 검사와 실행 테스트의 결과도 구분한다.
- 프론트와 백엔드는 서로 다른 개발자가 맡으며 같은 기능 스펙·공통 계약·FR별 검증 연결을 사용한다. 역할별 변경 범위·계약 전달·단독 검사·실제 연동 완료 기준의 원본은 [프론트·백엔드 작업 구분](../specs/development-roles.md)이다. 후속 계획과 작업은 이 역할 구분을 반영한다.

## GitHub 이슈와 PR

스펙을 기준으로 개발하면서 이슈와 PR을 함께 사용한다. 스펙은 기능·설계·작업의 기준이고, 이슈는 담당과 진행 상태, PR은 실제 변경과 검증 결과를 관리한다. 상세 기능 규칙을 이슈·PR에 복사하지 않는다.

### 개발 단계별 이슈 작성 시점

모든 스펙에 같은 순서를 적용한다. **개발을 맡긴 요청에서는 명세 준비 후 상위 이슈를 연결하고, 설계·작업 목록 검사 후 확정된 개발 범위의 세부 작업 이슈를 모두 연결하며, 작업 이슈 배정 후 코드를 구현한다.** 기존 산출물·이슈가 있으면 확인해 재사용한다. 사용자가 단계마다 이슈 생성을 따로 지시해야 하는 방식으로 운영하지 않는다.

| 시점 | 수행할 일 | 이슈의 상태·연결 |
|---|---|---|
| 명세 작성·필요한 명확화·명세 품질 확인 후, 상세 설계 시작 전 | 해당 스펙의 상위 이슈를 찾고 없으면 생성 | 스펙 경로·범위·완료 기준 연결. 세부 작업 준비 전에는 `backlog` |
| 설계·계약·작업 목록 작성 중 | 같은 상위 이슈에 준비 범위·진행·차단 사유 기록 | 준비 담당 조정은 아래 절차 적용. 미완성 작업을 배정 가능한 세부 이슈로 등록하지 않음 |
| `spec.md`·`plan.md`·계약·`tasks.md` 검사와 등록할 범위의 설계 충돌·누락 해결 후 | 확정된 개발 범위 전체를 독립 배정·PR·완료 확인 가능한 세부 이슈로 묶어 생성 | 실제 상위·서브 관계, 작업 식별자·포함 ID·역할·검사 기준 연결. 착수 조건에 따라 `ready` 또는 `blocked` |
| 코드 구현 시작 직전 | 작업 이슈의 최신 담당·선행 조건·진행 PR 확인 후 배정 | 선택한 작업을 `in-progress`로 변경. 사람 미지정이면 임의 배정하지 않음 |
| 구현·단독 검사 후 | 작업 이슈에 PR과 검사 증거 연결 | `in-review`. 실제 연동이 남으면 상위 이슈는 유지 |
| PR 병합·작업 완료 조건 확인 후, 최종 연동 확인 후 | 작업 이슈를 완료하고 마지막에 스펙 전체 완료 판단 | 작업과 상위 이슈의 종료 조건은 아래 완료 절차 적용 |

여기서 일관성 검사는 **명세에 필요한 일이 설계와 작업 목록에 빠짐없이 연결되고, 내용·계약·선행 순서가 서로 충돌하지 않는지 확인하는 것**이다. 이슈 작성 시점을 정하는 개발 절차와는 구분한다. 작업 목록 작성만으로 이 검사를 수행했다고 표시하지 않는다. 문제가 있으면 영향받는 작업 묶음을 고친 뒤 다시 검사하며 이미 준비된 다른 범위를 함께 막지 않는다.

요청 범위도 같은 기준으로 처리한다. 전체 개발을 맡긴 경우 위 단계의 이슈 등록을 포함해 이어간다. “스펙만”, “설계만”, “작업 목록 작성”, “검사만”처럼 산출물 작성·검사로 범위를 한정한 요청은 해당 결과까지만 수행하고 새 GitHub 이슈를 생성하지 않는다. “작업 이슈 준비”·“개발 준비와 이슈 등록”은 검사와 이슈 등록까지 수행하되 코드를 구현하지 않는다. 문서만 준비한 스펙을 나중에 개발할 때는 기존 단계 결과를 확인하고 누락된 상위/세부 이슈를 연결한 뒤 착수한다.

로컬에서 가능한 개발 이슈는 물리 서버·실기기 미정만으로 `blocked`로 만들지 않는다. 실제 서버/기기가 필요한 확인은 별도 작업으로 두고 그 작업의 선행 조건·미수행 상태를 관리한다. 계약 예제로 가능한 프론트 단독 개발과 실제 API/실기기 연동의 착수 조건도 구분한다.

| 용도 | 사용할 템플릿 |
|---|---|
| 스펙 전체 추적 | [스펙 진행](../.github/ISSUE_TEMPLATE/00-spec-tracking.md) |
| 담당별 개발 작업 | [개발 작업](../.github/ISSUE_TEMPLATE/01-development-work.md) |
| 기존 요구사항과 다른 동작 | [버그](../.github/ISSUE_TEMPLATE/02-bug-report.md) |
| 제품 요구사항·공통 계약 변경 | [스펙 변경](../.github/ISSUE_TEMPLATE/03-spec-change.md) |
| 변경 제출·검증 결과 | [PR](../.github/pull_request_template.md) |

이슈·PR 작성은 위 저장소 템플릿 파일을 직접 읽고 본문으로 사용한다. 템플릿의 제목·항목·기본 완료 조건을 유지하며 값과 해당 작업의 구체적인 검사만 채운다. 작성자용 주석이나 작업 번호 사용법 같은 반복 안내를 공개 본문에 넣지 않는다. 담당자는 GitHub Assignees, 추가 사람 리뷰 요청은 PR Reviewers로 관리하며, 이슈 본문에 미배정 안내나 이슈를 등록·연결했다는 작업 보고를 반복하지 않는다. 등록 전후에 원본 작업 ID·선행 조건·라벨·PR 연결을 확인한다. FR·SC는 원본 작업의 요구사항 구간만 읽고 spec.md에 존재하는 번호인지와 포함 작업의 실제 연결이 일치하는지 대조한다. 작업 번호·HTTP 상태값·해시·다른 스펙 번호를 요구사항으로 취급하지 않는다.

작업 이슈의 `관련 PR`에는 해당 작업의 변경을 수행하는 PR만 연결하고, 아직 없으면 `없음`으로 적는다. 설계·준비 문서 PR은 상위 스펙 이슈에서 연결하며 작업 이슈에서는 원본 문서 링크를 사용한다. PR 본문도 실제 변경 범위의 이슈만 연결한다. GitHub의 과거 참조 기록은 현재 본문 연결과 구분한다.

1. [단계별 시점](#개발-단계별-이슈-작성-시점)에 따라 명세 준비 후 기능 전체를 추적할 상위 이슈를 연결한다. 기존 이슈가 있으면 재사용한다. 예: `[001][SPEC] 개발 기반 구성`.
2. 설계·작업 목록 검사 후 독립 담당·검토·완료 판단이 필요한 작업을 역할별 세부 이슈로 연결한다. 프론트·백엔드와 실제 연동의 완료 상태를 나누되 작은 코드 수정마다 이슈를 만들지는 않는다. 역할과 공통 파일 변경 책임은 [역할 구분](../specs/development-roles.md)을 따른다.
3. 이슈에는 관련 스펙·FR·작업 ID·선행 이슈·계약·검사 기준을 연결한다. `tasks.md`는 구현 작업의 기준이며, 이슈에는 담당·진행·차단 원인·PR을 기록한다. 작업 내용이 바뀌면 원본 작업부터 고친다.
4. 개발 이슈에서 작업 브랜치를 만들고 PR로 변경을 제출한다. 한 PR은 독립적으로 검토할 수 있는 범위로 묶고 관련 이슈·스펙·작업·실제 검증 결과를 연결한다. 프론트 PR과 백엔드 PR을 따로 제출할 수 있다.
5. 해당 이슈의 완료 조건을 모두 충족하는 PR에만 `Closes #번호`를 쓴다. 일부 작업만 끝냈다면 `Refs #번호`로 연결한다. 역할별 PR이 합쳐져도 실제 연동이 남으면 기능 전체 추적 이슈는 열어 두며, 필수 연동 검사를 마친 뒤 닫는다.

기능 번호와 작업 번호를 함께 식별한다. 예를 들어 `001/T001`과 `004/T001`은 다른 작업이며, 기존 기능 명세의 검증 `T01`과도 다르다. 설치된 `$speckit-taskstoissues`는 작업 번호만으로 중복을 판단하고 작업마다 개별 이슈를 생성하므로 프로젝트의 기본 이슈 생성에 그대로 사용하지 않는다. 아래 에이전트 절차에 따라 독립 배정 가능한 작업을 묶고, 열린 이슈와 닫힌 이슈 모두에서 스펙 폴더·작업 식별자와 포함된 작업 ID를 확인한다. 일부 작업이 기존 이슈에 포함되어 있으면 기존 범위를 확인해 재사용하거나 나머지만 분리하며 같은 작업을 두 이슈에 중복 배정하지 않는다. Git 원격과 대상 저장소가 일치하는지도 확인한다. 작업 ID만 같다는 이유로 다른 기능의 이슈를 재사용하지 않는다.

### PR 리뷰와 수정

기본 흐름은 **작업 → 자체 검사 → 일반 PR → CodeRabbit 리뷰 → 지적 확인·수정·재검사 → 병합**이다. 문서 PR에도 적용하며, 문서라는 이유나 해당 스펙의 코드 구현이 남았다는 이유로 작성·검사를 마친 PR을 초안으로 유지하지 않는다. 초안은 해당 PR의 변경이 작성 중이거나 검토에 필요한 준비가 남았을 때 사용하고 남은 조건을 PR 본문에 적는다.

- 검토 준비 상태로 제출하면 설치된 CodeRabbit이 저장소 설정에 따라 리뷰한다. 작성 에이전트는 최신 커밋 대상의 리뷰 본문·인라인 지적·관련 상태 검사를 확인한다. 상태가 성공이라는 이유만으로 리뷰 내용을 읽지 않고 완료 처리하지 않는다.
- 지적의 타당성을 명세·설계·실제 변경과 대조하고 현재 작업 범위 안의 필요한 수정을 진행한다. 무관하거나 타당하지 않은 제안은 근거를 기록하며 무조건 적용하지 않는다. 제품 요구사항이나 공통 계약의 새로운 결정을 요구하면 해당 결정만 사용자에게 확인한다.
- 각 조치 가능한 리뷰 댓글에는 반드시 해당 댓글의 답글로 처리 결과를 남긴다. 수정한 경우 변경 내용·수정 커밋·관련 검사 결과를 적고, 반영하지 않은 경우 그 이유와 근거를 적는다. 봇의 해결 표시나 PR 전체 요약만으로 답글을 대신하지 않는다.
- 수정 후 관련 검사를 다시 수행하고 푸시한 뒤 최신 변경에 대한 후속 리뷰를 확인한다. 리뷰 대기·실패·미수행을 구분해 알리고, 리뷰가 도착하지 않았거나 오류로 중단됐으면 리뷰 완료로 표시하지 않는다.
- 자체 검사와 CodeRabbit 리뷰는 구분한다. 별도 사람이나 다른 에이전트의 리뷰는 요청·저장소 규칙에 따라 추가하며, CodeRabbit 외의 검토자를 매 작업마다 필수로 만들지는 않는다.
- 리뷰 대응은 개발 요청의 기본 범위에 포함한다. 병합과 이슈 종료는 사용자가 맡긴 범위 및 필수 검사·완료 조건을 확인한 뒤 수행한다. 이 문서는 자동 병합이나 상시 리뷰 감시를 설정하지 않는다.

### 작업 목록 준비와 등록 범위

기본 운영은 **전체 스펙의 상위 이슈를 목록으로 등록하고, 서브 이슈는 설계·검사를 마친 개발 범위 전체를 등록**하는 방식이다. 상위 이슈는 `[001][SPEC] 개발 기반 구성`처럼 스펙 하나를 추적하며, 목록에 있다는 이유로 즉시 착수 가능한 것은 아니다. 전체 작업 목록 초기화를 요청받으면 현재 스펙 목록을 기준으로 등록한다. 특정 기능 개발 요청에서는 그 범위의 상위 이슈를 찾고 없을 때 생성하며, 요청 밖의 전체 스펙을 임의 등록하지 않는다.

서브 이슈는 [단계별 시점](#개발-단계별-이슈-작성-시점)에 따라 설계·작업 목록을 검사한 뒤 생성한다. 검사를 마친 개발 범위의 작업은 빠짐없이 등록하고 상위 이슈에서 전체 순서를 볼 수 있게 연결한다. 선행 작업이 남아 있어도 이슈를 등록하며, 착수 가능한 작업은 `ready`, 선행 작업·환경·결정을 기다리는 작업은 `blocked`로 표시하고 구체적인 조건을 적는다. 아직 설계·검사를 마치지 않은 후속 스펙의 세부 작업까지 임의 생성하지 않는다. `tasks.md` 항목을 한 줄씩 반드시 이슈로 만들지는 않으며 한 담당자가 구현하고 하나의 PR로 검토·완료 확인할 수 있는 결과로 묶는다. 역할이 같아도 서로 따로 전달할 수 있는 결과는 나눈다. 묶음 사이 선행 관계가 순환하지 않는지 확인하고 모든 작업 ID가 정확히 한 묶음에 포함되게 한다.

스펙 상위 이슈는 `kind:spec`, 서브 작업은 `kind:work`로 구분한다. 버그는 `kind:bug`, 요구사항·계약 변경 제안은 `kind:change`를 사용한다. 상태 표시는 `status:backlog`(상위 목록·아직 준비 전), `status:ready`(가져갈 수 있음), `status:blocked`(선행 작업·결정 대기), `status:in-progress`, `status:in-review`, `status:done` 중 하나만 둔다. 위 이름은 준비할 라벨 규칙이며 문서 작성만으로 GitHub 라벨이 생성된 것은 아니다.

진행 상태의 기준은 GitHub 이슈의 열림·닫힘과 `status:*` 라벨이다. 이슈 본문과 문서 작업표에는 같은 진행 상태를 복사하지 않고, 차단 이유와 필요한 결과를 적는다. 완료 조건을 충족해 이슈가 닫히면 `status:done`으로 바꾸고 이전 상태 라벨을 제거한다. PR의 자동 종료 기능만으로 라벨이 갱신됐다고 취급하지 않는다.

상위 이슈의 `status:ready`는 최소 한 개의 서브 작업을 가져갈 수 있다는 뜻이며 전체 작업의 선행 조건이 끝났다는 뜻은 아니다. 작업 이슈의 역할 라벨과 변경 영역은 [배정 기준](../specs/development-roles.md#여러-개발자의-작업-배정)을 따른다.

### 작업 준비가 겹칠 때

고정 준비 담당자를 두지 않는다. 요청받은 역할·범위에 맞는 `ready` 이슈가 있으면 바로 선택하고, 없으면 개발 요청을 받은 사람이 필요한 설계·작업 분리·이슈 생성을 수행한 뒤 개발을 이어간다. 준비만 요청받았다면 준비까지만 수행한다.

준비 시작 전에 기존 준비 요청·진행 PR·상위 이슈의 준비 기록을 확인하고, 준비 중인 사람·범위·관련 요청 또는 PR을 상위 이슈에 기록한다. 같은 범위를 이미 준비 중이면 기존 작업에 연결하며, 다른 사람은 준비된 이슈나 다른 범위의 작업을 진행할 수 있다. 준비 중이라는 이유로 해당 스펙 전체를 차단하지 않되, 같은 `plan.md`·`tasks.md`·계약·공통 파일을 변경할 때는 겹치는 범위를 조정한다.

이슈 생성 직전에 열린 이슈와 닫힌 이슈를 다시 조회한다. 상위 이슈는 스펙 폴더, 서브 이슈는 스펙 폴더·작업 식별자·포함된 작업 ID로 비교해 기존 이슈가 있으면 재사용한다. 생성 직후에도 같은 식별자의 이슈와 상위·서브 관계를 확인한다. 상위 이슈가 없을 때 생성하는 경우에도 이 확인 절차를 적용한다.

준비 완료·중단 시 진행 기록과 남은 범위를 갱신한다. 중단된 준비는 남은 결과를 확인한 사람이 이어받을 수 있으며 특정 사람의 복귀를 기다리지 않는다. 동시 준비나 중복 이슈를 발견하면 겹치는 문서 변경·이슈 생성만 멈추고 한쪽으로 모은다. 유지할 이슈에 빠진 작업·PR·선행 관계를 연결한 뒤 나머지는 중복 사유와 유지 이슈를 남겨 닫는다. 구현 작업을 중복 완료로 처리하지 않는다.

중복 이슈를 닫기 전에 상위·서브 이슈 관계, 다른 작업이 참조하는 선행 이슈, 관련 PR의 `Closes`·`Refs` 대상을 확인하고 유지할 이슈로 옮긴다. 유지할 이슈의 완료 조건을 모두 충족하지 않는 PR은 `Refs`로 연결한다. 닫힌 중복 이슈를 다시 발견하면 중복 사유에 연결된 유지 이슈를 따라가며, 중복 이슈를 다시 배정하거나 닫힘을 선행 작업 완료의 증거로 사용하지 않는다. 유지 이슈의 실제 완료 조건과 증거를 확인해 후속 작업의 착수 가능 여부를 판단한다.

별도 잠금이나 대기열을 필수로 두지 않고 생성 전후 확인과 중복 정리로 운영한다. 두 사람이 정확히 동시에 생성하면 중복이 생길 수 있으므로, 발견한 중복은 위 절차로 정리한 뒤 해당 작업을 배정한다. 다른 스펙의 준비와 이미 준비된 작업의 개발은 병렬로 진행할 수 있다.

### 개발 요청에 따른 에이전트 진행

이 절은 개발 요청을 받은 에이전트가 수행할 절차다. GitHub Actions나 상시 실행 봇을 설치했다는 뜻은 아니다. 산출물만 요청한 경우와 이슈 준비까지 맡긴 경우의 범위는 [단계별 시점](#개발-단계별-이슈-작성-시점)을 따른다.

1. 원격 저장소·GitHub 로그인 계정·권한을 확인하고 해당 스펙의 열린/닫힌 상위 이슈·서브 이슈·PR을 조회한다. 상위는 스펙 폴더, 서브는 스펙 폴더와 작업 식별자를 함께 비교해 중복을 막는다. 닫힌 이슈도 완료 증거와 현재 범위를 확인하며, 같은 작업을 다시 생성하지 않는다. 취소·미완료로 닫힌 작업은 사유를 확인해 기존 이슈를 이어간다.
2. 관련 `spec.md`를 확인한다. 없으면 필요한 명세·명확화·품질 확인을 수행하고, 준비된 스펙의 상위 이슈를 재사용하거나 없으면 생성한다. 이어서 계약·`plan.md`·`tasks.md`를 확인하고 부족한 설계·작업은 [준비 조정 절차](#작업-준비가-겹칠-때)에 따라 작성한다. 준비된 결과를 다시 만들지 않으며 구현 전에 일관성을 검사한다. 기존 21개 기능 범위를 다시 나누거나 상세 정책을 이슈에 복사하지 않는다.
3. 검사 결과를 반영한 현재 요청 범위의 확정된 작업 전체가 서브 이슈에 빠짐없이 연결되도록 부족한 이슈를 생성한다. 템플릿으로 스펙·FR·작업 ID·역할·변경 영역·선행 관계·검사·인수 결과를 채우고 실제 GitHub 서브 이슈 관계로 연결한다. 새 역할·상태 라벨이 없으면 요청 범위에서 재사용 가능한 라벨을 준비한다.
4. 선행 조건과 공통 파일 충돌을 확인해 `ready`와 `blocked`를 구분한다. 착수에 필요한 결과와 최종 연동에 필요한 결과를 작업별로 따로 적는다. 기본은 main에 병합된 선행 결과를 사용한다. 선행 변경의 병합 전에 시작한다면 사용할 브랜치·커밋·PR과 준비된 결과를 명시한다. API 계약과 예제 응답이 준비되면 프론트의 단독 개발을 서버 구현 대기로 막지 않는다. 실제 연동 작업은 필요한 양쪽 구현이 준비될 때 시작한다.
5. 이슈 번호가 지정되면 해당 작업을, 역할만 지정되면 그 역할의 미배정 `ready` 작업을 찾는다. 여러 후보는 스펙의 우선순위·선행 관계에 따라 선택하고 선택 결과를 알린다. 역할이나 작업 범위가 전혀 없으면 임의로 참여자의 역할을 정하지 않고 작업 가능한 후보를 안내한다.
6. 착수 직전 최신 담당자·상태·진행 PR을 다시 확인하고 작업자를 배정한 뒤 `in-progress`로 표시한다. 다른 담당자가 맡았으면 가져가지 않는다. 배정 후 다시 조회해 자신의 배정과 단독 작업 여부를 확인한다. GitHub 배정은 잠금 기능이 아니므로 동시 선택이 발견되면 코드 변경 전에 조정한다. 현재 CLI 계정이 사람이 지정한 작업자 계정과 같은지도 확인한다.
7. [이슈 단위 구현 범위](#이슈-단위-구현-범위)에 따라 선택한 작업 ID만 작업 브랜치에서 개발·검사하고 템플릿으로 PR을 생성한다. PR 생성만으로 구현 완료를 표시하지 않는다. 단독 검사와 실제 연동을 구분하고 PR은 `in-review`로 연결한다. 자체 검사를 마쳤으면 일반 PR로 제출하거나 초안을 검토 준비 상태로 전환하고, [리뷰 절차](#pr-리뷰와-수정)에 따라 CodeRabbit 지적 확인·수정·재검사까지 기본으로 이어간다. 병합은 사용자가 맡긴 범위에서 수행한다.
8. `tasks.md` 체크는 해당 구현 작업과 검사가 끝났을 때 갱신하며, PR 병합과 GitHub 작업 이슈 완료는 별도로 판단한다. PR이 실제 병합되고 이슈의 완료 조건을 충족하면 이슈를 완료하고 작업 체크와 증거 연결을 다시 확인한다. 남은 검사가 있으면 작업 완료로 닫지 않는다. 완료된 선행 작업에 의해 다른 작업이 준비되는지도 확인한다.
9. 별도 검증 작업은 스펙의 FR·SC·검증 기준을 합쳐진 코드와 대조하고 필요한 실제 연동·실기기 검사 결과와 누락 항목을 남긴다. 스펙 전체 완료는 상위 이슈에서 모든 필수 서브 작업의 병합·완료 증거와 검증 결과를 모아 판단한다. 필수 누락은 기존 작업 보완 또는 추가 서브 이슈로 연결한다. 자식 이슈 수가100%라는 이유로 상위 이슈를 자동 완료하지 않는다. 필수 결과를 충족한 뒤 관련 스펙의 상태와 상위 이슈를 갱신한다. 보류 항목이 남으면 완료된 범위와 미완료 범위를 명시한다.

개발자는 “프론트 작업 가능한 이슈 하나를 가져와 진행해줘”, “이슈 #번호를 진행해줘”, “001 작업 이슈를 준비해줘”처럼 요청할 수 있다. 마지막 요청은 작업 준비까지만이며 구현은 하지 않는다. 목록에서 적합한 이슈가 없으면 맡긴 범위의 미완료 스펙·준비된 설계를 확인해 필요한 작업을 준비하고, 선행 작업이 없어 착수할 수 없다면 `blocked` 사유를 알린다.

템플릿 파일은 기본 브랜치에 반영되어야 GitHub에서 사용할 수 있다. 템플릿 작성·이슈 생성·PR 생성·원격 반영 상태를 구분한다. 라벨과 서브 이슈 관계·배정은 템플릿만으로 자동 설정되지 않으며 위 에이전트 절차나 GitHub 작업으로 설정한다.

## 현재 기능 선택

기능 선택은 Git 브랜치와 별개다. `.specify/feature.json`의 `feature_directory`를 해당 `specs/` 폴더로 맞추고 전제 검사 결과의 경로를 확인한다.

같은 작업 폴더에서 병렬 작업할 때는 각 작업에 `SPECIFY_FEATURE_DIRECTORY`와 `SPECIFY_FEATURE_NO_PERSIST=1`을 함께 지정한다. 경로만 지정하면 일부 스크립트가 공용 `.specify/feature.json`을 덮어쓴다. 저장 방지 설정은 해당 작업의 모든 하위 스크립트에도 전달한다.

`$speckit-specify`는 스크립트 밖에서도 `.specify/feature.json`을 직접 기록하므로 위 설정만으로 새 스펙의 병렬 생성을 보호할 수 없다. 같은 작업 폴더의 새 스펙 생성과 공용 선택 파일 변경은 한 작업씩 진행한다. 각 작업이 사용할 스펙 폴더와 번호를 먼저 정한 뒤, 병렬 설계·구현은 각자의 경로와 저장 방지 설정으로 실행한다.

전체 개발 단위·기능별 원본 연결·선행 관계는 [스펙 목록](../specs/README.md), 개발 준비 상황은 [개발 시작 안내](development.md), 작업 진행 상태는 해당 GitHub 이슈에서 확인한다.

## 설치와 확인

도구는 프로젝트의 `.tools/`에 설치하며 이 폴더는 Git에서 제외한다. 설치 파일은 공식 GitHub 릴리스 `v1.1.0`, 소스 커밋 `f1d3a4f8337ebbd3ae22760a9c12e3352b93a175`다. 새 환경에서는 Python 3.11 이상과 uv를 준비한 뒤 루트에서 설치한다.

```sh
UV_TOOL_DIR="$PWD/.tools/uv-tools" UV_TOOL_BIN_DIR="$PWD/.tools/bin" uv tool install specify-cli --from 'git+https://github.com/github/spec-kit.git@v1.1.0'
```

프로젝트 루트의 다음 명령은 설치한 도구와 설정을 확인한다. 외부 폴더에서 실행해도 `scripts/specify`는 이 프로젝트를 대상으로 동작한다.

```sh
./scripts/specify version
./scripts/specify integration status --json
.specify/scripts/bash/check-prerequisites.sh --json --paths-only
python3 scripts/check-docs.py
```

`.agents/skills`의 설치된 스킬을 에이전트가 인식해야 한다. 현재 세션 목록에 없으면 프로젝트를 다시 열고 설치 폴더를 확인한다. 스킬 선택은 명령 등록과 프로젝트 규칙으로 운영하며 자동 실행 서비스는 아니다.

앱 코드가 생기면 [개발 시작 안내](development.md)에 실제 설치·실행·타입 검사·빌드·테스트 명령을 추가한다. 문서 검사는 기능 검사나 Spec Kit의 의미 검사를 대신하지 않는다.

## 설정 변경

버전 업그레이드는 설치 버전과 변경 내용을 확인한 뒤 진행한다. `init --force`로 갱신하기 전에 프로젝트 원칙과 수정한 설정을 보관하고 변경 파일을 확인한다. 설치된 스킬·템플릿을 직접 고치는 대신 프로젝트 원칙과 운영 문서로 규칙을 연결한다.
