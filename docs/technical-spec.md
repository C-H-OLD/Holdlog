# Holdlog(가제) — 기술·운영 명세

현재 채택한 기술과 운영 기준, 구현할 때 지켜야 할 조건을 정리한다. 제품 동작은 [기능 명세](./functional-spec.md)와 [기록 관계 설계](./record-relationships.md)를 따른다. 세부 구현 제안은 확정 요구사항과 구분한다. 남은 선택은 [미결정 사항](./open-questions.md), 실제 설정·검증 작업은 [초기 설정 준비](./setup-checklist.md)에서 관리한다. 설치·구현·배포는 아직 진행하지 않았다.

## 1. 현재 정한 방향

|---|---|
| 이름 | Holdlog(가제) |

로그인 선택과 앱 배포 설정은 별개다. iOS·Android의 앱 식별자, 개발자 계정, 서명, 시험 배포와 스토어 등록 설정은 아직 준비해야 한다. 최초 지원 지점 목록과 실제 등록 데이터도 필요하다.

## 2. 서버·DB·푸시 — 확정

**NestJS + TypeScript API 서버, PostgreSQL DB**를 사용한다. [NestJS 공식 문서](https://docs.nestjs.com/first-steps)

| 부분 | 구성 | 이유·조건 |
|---|---|---|
| API | NestJS + TypeScript, 하나의 서버 안에 계정·크루·기록·암장·미디어 기능 분리 | 연결·삭제·권한 규칙을 한곳에서 관리. 시작부터 여러 독립 서버로 쪼개지 않음 |
| 운영 DB | 물리 서버에 PostgreSQL 직접 운영 | 컨테이너와 별도로 데이터를 보존할 영구 볼륨 사용 |
| 개발 DB | 로컬 Docker PostgreSQL | 운영과 같은 주요 버전으로 개발·검증 |
| 서버 배포 | 물리 서버에서 Docker Compose | API·DB·작업 처리기를 나눠 실행. 실제 OS·CPU 구조와 가용 자원을 확인한 뒤 구성 |
| 관리자 웹 | React + TypeScript, 같은 물리 서버에서 제공 가능 | 데이터 등록 화면 중심. 모바일 앱과 별도 배포 |
| 백그라운드 작업 | 물리 서버의 별도 작업 처리기. pg-boss(PostgreSQL 기반) 사용 | 변환·삭제 재시도·알림 처리. 재시작 후 재개·중복 처리 방지·DB 부하 검증 |

Docker Compose로 단일 서버에서 API·DB·작업 처리기를 실행한다. [Compose 운영 안내](https://docs.docker.com/compose/how-tos/production/)

개발 단계에서는 앱·API·DB·파일 저장 기능을 구현하고 실제 기기에서 검증하는 데 집중한다.

앱과 관리자 웹은 API를 통해 DB에 접근한다. 공동 방문·참석·개인 기록 연결 변경은 DB 트랜잭션으로 묶는다. 로그인 제공자와 해당 제공자의 사용자 식별자로 계정을 구분한다. 구글·Apple 로그인 계정은 자동 연결·병합하지 않는다. 같은 이메일이어도 각각의 계정으로 취급하며, 기존 동일 제공자·식별자로 재로그인하면 기존 계정을 사용한다. 수동 계정 연결 UI는 현재 범위에 추가하지 않는다.

### 작업 대기열·미디어 자원 — 확정

작업 대기열은 시간이 걸리는 작업의 할 일 목록이다. pg-boss를 사용한다. 지연 실행·실패 재시도를 지원한다. [pg-boss 공식 문서](https://github.com/timgit/pg-boss)

- API는 기록을 저장하고 작업을 등록한다. 작업에는 파일 내용 대신 파일 ID·작업 ID를 넣는다.
- 영상 변환은 별도 Docker 작업 처리기에서 초기 동시 실행 1개로 시작한다. 알림·삭제 작업은 다른 처리기로 실행해 긴 영상 변환을 기다리지 않게 한다.
- 기록 저장과 작업 등록은 같은 DB 트랜잭션 또는 발송 대기 테이블로 일관성을 유지한다. 서버 재시작·재시도에도 변환 결과·삭제·알림이 중복 반영되지 않게 작업별 식별자와 상태를 검사한다. 외부 푸시 전달까지 정확히 한 번이라고 보장하지 않는다.
- CPU·메모리 제한은 서버 사양에 맞춰 Docker 설정으로 조정한다. 1080p 출력은 유지하고 실제 영상으로 품질·속도·파일 크기를 확인해 압축 설정을 정한다. 하드웨어를 모르는 상태에서 고정 자원값을 확정하지 않는다.
- 처리 중인 파일 자체나 해당 파일을 삭제 대상으로 포함하는 개인 기록·계정이 삭제되면 새 변환본을 공개하지 않고 정리한다. 공동 방문만 삭제된 경우에는 공동 공유를 해제하고 업로더의 개인 보관·진행 중 업로드·변환은 유지한다. 알림 실행 직전에는 일정 상태·대상·이미 발송한 사건인지 재검사한다.

### Firebase 푸시

푸시는 Firebase Cloud Messaging(FCM)을 사용한다. 발송 시점·대상·권한·중복 방지는 물리 서버가 처리하고 Firebase는 기기로 알림을 전달한다. iOS 전달을 위해 Firebase에 APNs 인증 키를 설정한다. [Firebase 공식 설정](https://firebase.google.com/docs/cloud-messaging/ios/get-started)

FCM을 사용하며, 클라이언트 연동은 React Native Firebase Messaging을 우선 구현안으로 둔다. 해당 네이티브 모듈을 포함한 Expo 전용 개발 빌드에서 검증한다. Firebase 푸시 선택으로 DB·파일 저장 위치나 구글·Apple 로그인 정책이 바뀌지 않는다.

### Expo — 확정

Holdlog는 React Native + Expo + 전용 개발 빌드를 사용한다. 이는 Expo Go만으로 개발한다는 뜻이 아니며, Firebase 등 필요한 네이티브 모듈을 포함한다. 자체 서버·로컬 파일 저장을 그대로 사용할 수 있다. Expo의 클라우드 빌드 서비스는 필수가 아니고 로컬 빌드도 가능하다. iOS 로컬 빌드는 macOS와 Xcode가 필요하다. [RN 공식 시작 안내](https://reactnative.dev/docs/environment-setup), [Expo의 Firebase 연동](https://docs.expo.dev/guides/using-firebase/), [로컬 빌드](https://docs.expo.dev/guides/local-app-development/)

## 3. 모바일 지도 — 현재 기능의 지도 사용료 0원

**아래 구성·사용 조건으로 기본 모바일 지도를 구현한다. 비용 확인 근거의 날짜와 범위는 기술 선택 기록에서 관리한다.**

| 플랫폼 | 사용할 구성 | 공식 정책과 비용 |
|---|---|---|
| Android | react-native-maps + Google Maps SDK for Android, Map ID 미설정 | Maps SDK의 무료 사용량이 Unlimited로 명시됨. 기본 지도 표시 사용료 0원 |
| iOS | react-native-maps + 기본 Apple MapKit | Apple 기술지원의 네이티브 MapKit 안내에 따라 지도 사용량에 따른 추가 요금 없음 |

### 현재 기능과 구현 조건

- 지도 표시·이동·확대·축소, 등록한 암장 좌표 표시, 암장 선택·상세 열기를 구현한다.
- 현재 위치는 기기의 위치 기능으로 받아 지도에 표시한다. 별도의 Google Geolocation API를 호출하지 않는다.
- 브랜드·지점·지역 검색과 암장 정보는 관리자가 등록한 우리 서버 DB로 처리한다. 외부 Places·Geocoding·Routes·Street View API를 호출하지 않는다.
- Android는 Google Maps API 키와 결제 계정을 설정한다. API 키를 설정해도 위 기본 지도 표시에는 사용료가 발생하지 않는다. `googleMapId`는 설정하지 않아 무료 Maps SDK 범위로 구현한다.
- iOS는 기본 Apple 지도 공급자를 사용하며 별도 지도 API 키를 발급하지 않는다.
- 지도 이미지를 우리 서버에서 생성·제공하지 않는다. 우리 서버는 암장 좌표와 기록을 관리한다.

### 비용·설정 기준 링크

[Google 요금표](https://developers.google.com/maps/billing-and-pricing/pricing) · [Maps SDK 적용 조건](https://developers.google.com/maps/billing-and-pricing/sku-details) · [Android 설정](https://developers.google.com/maps/documentation/android-sdk/usage-and-billing) · [Apple MapKit 안내](https://developer.apple.com/forums/thread/127493). 조사 과정은 [기술 선택 기록](history/decisions/technical-selection.md)에서 확인한다.

정책 확인은 완료했다. 실제 앱 구현·API 키 설정·실기기 동작 및 사용 항목 확인은 아직 진행하지 않았다. 구현 완료 시 Android에 Map ID가 없고 Maps SDK만 사용하는지, iOS가 Apple MapKit을 사용하는지, 암장 검색이 자체 DB만 호출하는지 확인한다. 현재 위치를 거절하거나 지도 로딩에 실패해도 암장 목록·검색은 유지한다.

## 4. 미디어 처리 — 확정

**사진·영상은 보유한 물리 서버에 저장하며, 외부 저장소로 전환 가능한 구조는 필수다.** 영상 변환은 물리 서버의 FFmpeg 작업 처리기를 사용한다. API와 변환 작업을 분리하고 변환 동시 실행 수·CPU·메모리를 제한해 영상 처리 때문에 기록 저장이 느려지지 않게 한다. 실제 처리량은 서버 사양으로 검증한다. [FFmpeg 공식 문서](https://ffmpeg.org/ffmpeg.html)

기록은 먼저 저장하고 파일은 따로 올리는 D05를 유지한다. 재생본·사진 저장본·썸네일과 처리 중 임시 파일은 컨테이너를 교체해도 남는 서버의 전용 데이터 영역에 저장한다. 업로드 원본은 변환·검증을 위한 임시 파일로만 취급하며 영구 보관하거나 백업하지 않는다. 큰 파일의 이어 올리기와 재시작 후 복구는 로컬 저장 구현에서도 지원한다. 저장 영역을 일반 공개 폴더로 제공하지 않고, 읽기 요청마다 기존 공개 범위·소유권을 확인한다.

### 저장소 교체 설계 — 구현 필수 요구사항

- 기록 기능은 저장소 공통 인터페이스를 사용한다. 업로드 시작·이어 올리기·완료·취소, 파일 읽기(영상 구간 요청 포함)·정보 조회·삭제를 저장 방식과 분리한다.
- 첫 구현은 로컬 파일 저장 어댑터다. 외부 저장소의 특정 업체는 미정이며, 업체를 선택하면 같은 인터페이스의 어댑터를 추가해 전환할 수 있어야 한다. 외부 서비스 계약·실제 전환은 현재 작업이 아니다.
- DB에는 안정적인 파일 ID, 저장소 ID, 저장 키, 크기·체크섬·처리 상태를 보관한다. 절대 디스크 경로나 업체 URL을 개인 기록의 식별자로 사용하지 않는다.
- 사진 저장본·영상 재생본·썸네일과 처리 중 임시 파일의 위치를 추적한다. 앱은 우리 서비스의 파일 ID로 접근하므로 저장소가 바뀌어도 기록 연결과 앱 API는 유지한다.
- 신규 업로드의 기본 저장소만 바꿔도 기존 파일은 원래 저장소에서 읽고 지울 수 있어야 한다. 저장소 설정 변경이 기존 파일까지 자동 이동시킨다는 뜻은 아니다.
- 기존 파일 이동은 복사 → 크기·체크섬 확인 → DB 위치 전환 → 정상 읽기 확인 → 이전 사본 정리 순서로 수행한다. 중단 시 재개할 수 있고 검증 전에는 이전 저장소의 보관 파일을 지우지 않는다. 이는 업로드 원본을 장기 보관한다는 뜻이 아니다.
- 이동 중 삭제·비공개 전환도 같은 권한 규칙을 따른다. 삭제된 파일이 늦게 끝난 복사·변환 때문에 다시 생기지 않게 하고 양쪽 저장소의 사본 정리를 재시도한다.
- 개발 완료 기준에는 로컬 저장, 저장소가 섞인 상태의 읽기·삭제, 이동 실패 후 재개, 비공개 파일 접근 차단을 포함한다. 특정 외부 어댑터의 실제 연동 검증은 업체 선택 후 수행한다.

| 대상 | 확정 방식 |
|---|---|
| 사진 입력 | JPEG·PNG·HEIC. 중간 품질로 방향 보정한 사진 저장본과 미리보기 생성. 업로드 원본을 별도로 중복 보관하지 않음 |
| 영상 입력 | MP4·MOV. 확장자뿐 아니라 실제 영상·음성 코덱 검사 |
| 영상 재생 | 초기에는 H.264/AAC MP4, 최대 1080p 재생본과 썸네일. 작은 원본을 억지로 확대하지 않음 |
| 원본 | 변환 결과 검증·저장 완료 후 임시 원본 삭제. 실패 시 재시도용으로만 임시 유지 |
| 업로드 | 서버에서 권한 확인 후 선택한 저장소에 업로드. 큰 파일은 이어 올리기, 파일별 진행·실패 상태는 내부에서 관리. 실패 안내와 재시도는 기본 화면 위 공통 업로드 실패 다이얼로그로만 제공하며 썸네일에 실패 효과·아이콘·문구를 넣지 않음 |
| 변환 | 업로드 완료 뒤 물리 서버 작업 처리기에서 변환. 처리 중 표시, 실패해도 기록 유지 |
| 재생 배포 | 권한 확인을 거친 다운로드 경로. CDN은 추후 필요할 때 검토 |

영상은 가로형 최대 1920×1080, 세로형 최대 1080×1920 범위에서 비율을 유지하고 작은 원본은 확대하지 않는다. 1080p는 저장·재생본의 해상도 기준이며 업로드 길이·용량 제한이 아니다. 사진에는 이 영상 해상도 기준을 적용하지 않는다. 사진 저장 품질은 중간으로 확정한다. 구체적인 인코더 품질 수치·해상도는 이 기준에 맞춰 개발 중 샘플로 조정하며 별도 제품 결정으로 남기지 않는다. 제품상 용량·길이·개수 제한 없음은 유지한다. 실제 서비스에는 기술 한도가 있으므로 지원 가능한 파일·비용을 검증하고, 충돌하면 정책 변경을 별도로 논의한다.

모든 파일은 소유자와 업로드 대상 기록을 DB에서 추적한다. 이미 업로드된 파일 ID를 받아 다른 기록에 재첨부·이동하는 API는 제공하지 않는다. 개인 기록 연결에 따라 크루 방문 상세에서 첨부를 조회하는 관계는 유지한다. 개인 파일의 ‘공개’는 그 개인 기록이 연결된 크루의 활성 회원만 볼 수 있다는 뜻이다. 미연결 상태·다른 가입 크루에는 공개하지 않는다. 후기도 별도 공개 값을 같은 권한으로 검사한다. 인터넷 전체 공개 주소를 만들지 않는다. 비공개 미디어는 썸네일도 본인만 본다. 재생본에서 불필요한 위치 메타데이터는 제거하는 것을 추천한다.

짧은 만료 서명 URL만으로는 발급 직후의 권한 회수를 즉시 보장할 수 없다. 초기에는 요청마다 권한을 확인하는 미디어 전달 경로를 추천하며, CDN 캐시·영상 구간 요청도 같은 기준을 만족하는지 확인한다. 이미 사용자 기기에 내려받은 파일까지 회수할 수 있다는 의미는 아니다.

## 5. 저장소 운영 — 채택한 기준

‘저장소’는 코드, DB, 파일을 나눠 준비한다. 현재 개발에 필요한 코드 구성과 데이터 저장·삭제 기준을 다룬다.

### 코드

- 비공개 Git 저장소 하나에 `apps/mobile`, `apps/admin`, `apps/api`, `packages/contracts`, `docs`를 두는 구성으로 관리한다.
- 앱·관리자 웹·서버는 각각 배포한다. 공통 API 자료형만 공유하고 서버 권한 코드를 앱에 넣지 않는다.
- 사진·영상, 운영 DB 덤프, 비밀 키를 Git에 넣지 않는다. 운영 비밀값은 물리 서버의 접근 제한된 설정 파일 또는 별도 비밀 관리 도구로 관리한다.
- DB 변경 파일은 코드와 함께 관리하고, 배포 전에 시험 환경에서 적용한다.

### DB·파일 저장과 삭제

- 개발·시험과 운영의 DB·파일 저장 영역·접근 권한을 분리한다. 실제 사용자 자료를 개발용으로 복사하지 않는다.
- 개인 기록 삭제 시 해당 기록에 본인이 첨부한 파일, 계정 삭제 시 해당 계정 소유 파일, 파일 자체 삭제 시 해당 파일의 접근과 공유를 먼저 차단한다. 삭제 대상의 사진 저장본·영상 재생본·썸네일·임시 파일을 함께 삭제하고 실패한 삭제는 재시도한다. 개인 기록 삭제는 무관한 공동 파일·타인 파일을 삭제하지 않는다.
- 공동 방문만 삭제되면 공동 공유를 해제하고 개인 기록·업로더의 보관 파일은 유지한다. 진행 중 업로드·변환도 개인 보관용으로 계속 처리하며, 삭제된 공동 방문에 다시 연결하거나 공개하지 않는다.
- 정상 변환 원본은 결과 검증·파일 등록 완료 후 바로 삭제하고, 삭제 실패는 재시도한다. 실패·중단 상태로 7일간 진행이 없는 임시 파일은 정리하며 이후 재시도에는 재업로드가 필요함을 표시한다. 정상 진행 중인 업로드·변환 작업은 정리 대상에서 제외한다.

## 6. 기능 개발 이후에 다룰 운영 준비

백업 정책·저장 위치, 장애 복구 목표, 외부 접속용 도메인·HTTPS 구성, 배포 자동화는 기능 개발 이후에 검토한다. 지금의 개발 착수 조건이나 완료 기준에 포함하지 않는다. 백업 주기·보관 기간 등 구체적인 운영 수치는 그때 정한다.

## 7. 크루 초대 링크 — 첫 버전

- 모바일 딥링크로 S02 초대 가입 확인을 연다. 초대 코드·QR·공유 링크는 하나의 크루 초대 정보를 사용하며 QR에는 초대 링크를 담는다.
- 앱이 실행 중이거나 종료된 경우 모두 같은 초대를 처리한다. 로그인 전 초대는 로그인 후 이어가며, 가입 확인 전에는 자동 가입하거나 공동 데이터를 노출하지 않는다.
- 서버가 코드 유효성·현재 가입·재가입 차단 여부를 최종 검사한다. 링크에 전달된 크루 이름·역할을 권한 근거로 신뢰하지 않는다. 생성자를 제외한 초대 가입자는 일반 회원이다.
- 앱에 링크 경로·초대 식별자를 전달하고 OS의 공유 기능으로 링크를 보낸다. 미가입 크루의 공개 검색 API는 제공하지 않는다.
- 앱 미설치 시에는 설치 안내와 초대 코드로 가입을 이어갈 수 있게 준비한다. 설치 이후 초대를 자동으로 복원하는 기능을 전제로 삼지 않는다. 초대 공유 문구에 코드도 포함하고 설치 후 링크 다시 열기 또는 코드 입력을 안내한다.
- 실제 공개 링크 주소·도메인과 OS 연결 설정은 외부 접속 환경을 준비할 때 구성한다. 개발 중에는 개발용 링크로 가입 흐름을 검증하고 출시 전 실제 배포 링크를 기기에서 확인한다. 현재 도메인 구매·배포 작업을 시작한다는 뜻은 아니다.
