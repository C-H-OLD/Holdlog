# 관리자 웹 아키텍처

`apps/admin`의 코드 배치·상태 소유·API 소비 기준을 관리한다. 제품 동작은 [관리자 명세](../admin-spec.md), 화면은 최신 시안, 인증·HTTP 형식과 처리 의미는 공통 계약이 원본이다. 모바일 크루 관리와 서비스 관리자 웹을 구분한다.

## 적용 범위와 현재 상태

현재 React/Vite의 빈 실행 화면·개발 API proxy·연결 진단·합성 계약 소비와 Node 검사가 있다. A02·A03·A04 제품 화면과 관리자 인증은 구현 전이다. 아래 목표 폴더는 필요한 파일이 생길 때 만들며 문서 작성이 설치·구현·브라우저 검증 완료를 뜻하지 않는다.

기존 React·TypeScript·Vite 기반을 유지한다. 라우터·서버 캐시·폼·UI 라이브러리는 아직 설치된 것으로 가정하지 않으며 004·006·019의 상세 계획에서 실제 필요와 호환성을 확인한다. 모바일용 Router·Zustand·네이티브 UI를 어드민의 필수 도구로 복사하지 않는다.

## 화면과 기능 코드 배치

화면·API·훅·공용 부품을 역할별로 찾을 수 있게 배치한다. 화면마다 빈 feature 계층과 barrel을 만들지 않으며 복잡한 작업 조정만 필요할 때 기능 단위로 분리한다.

```text
apps/admin/
├── AGENTS.md
├── vite.config.ts             # Node 전용 개발 proxy·빌드 설정
├── node-checks/               # Node 설정 검사
├── checks/                    # 브라우저 환경·합성 계약 타입 검사
├── test/                      # 기존 Node 검사와 후속 검사
└── src/
    ├── main.tsx               # React 시작·공용 Provider 조립
    ├── pages/                 # 후속: 암장/브랜드·세팅·공지 화면
    ├── api/                   # 기존 계약 소비 + 후속 client·업무 API 함수
    ├── components/            # 후속: 공용 UI·화면별 폼 부품
    ├── hooks/                 # 후속: 조회·변경·입력/복귀 연결
    ├── providers/             # 후속: 관리자 세션·공용 상태 연결
    ├── lib/                   # 후속: 순수 입력·날짜·표시 변환
    ├── constants/             # 후속: 토큰·query key 등 역할별 상수
    ├── types/                 # 후속: 앱 내부 표시·입력 모델
    └── development/           # 기존 개발 연결 진단
```

화면은 폼·부품·훅을 조립하고 API 전송은 `api/`에서 관리한다. 브랜드·암장 API는 `api/catalog.ts`, 폼 부품은 `components/catalog/`, 세팅은 `pages/SettingsPage.tsx`처럼 책임이 드러나는 이름을 사용한다. 이는 배치 예시이며 URL·새 화면·라이브러리를 확정하는 것이 아니다.

화면 담당은 006(A02·A03)과 019(A04), 관리자 인증 소비는 004에 연결한다. 승인되지 않은 관리자 로그인 시안·회원 관리·대량 삭제 화면을 임의로 추가하지 않는다.

## 공용 UI와 API 호출 경계

공용 버튼·입력·확인창은 표시값과 콜백을 받고 세션·업무 API·특정 폼 상태를 직접 읽지 않는다. 화면 전용 폼은 `components/<업무>/`에 두고 실제 재사용 범위가 확인될 때 공용으로 옮긴다. 모바일 UI와 같은 패키지로 묶지 않는다. 문구·레이아웃·확인창은 [관리자 웹 화면](../screen-design.md#admin-web)을 따른다.

```text
화면·폼 → 조회/변경 훅 → 업무 API 함수 → 공통 HTTP client → 서버
                              ↘ @holdlog/contracts 공개 타입·검사 함수
```

- HTTP DTO를 수기로 복제하지 않는다. `/http`의 타입과 `/validators`·`/operations`의 값 검사 연결을 사용하며 서버 내부 코드를 가져오지 않는다. 폼 draft·표시 모델은 소비 경계에서 변환한다. 서버 응답을 타입 단언만으로 신뢰하지 않는다.
- client는 전송·기한·취소·인증 연결·공통 오류를 처리하고 화면이나 React Provider를 import하지 않는다. API 함수는 계약 요청·결과를 제공하며 폼 변경·화면 이동·캐시 갱신은 해당 훅/화면에서 조정한다.
- 네트워크 실패·timeout·취소·계약 위반·업무 오류를 구분한다. 조회 실패를 빈 목록으로 바꾸지 않고 서버의 임의 message를 화면 문구로 쓰지 않는다. 계약 code를 기존 공통 안내에 연결한다.
- 쓰기 시작 시 대상 ID·draft·version·멱등키를 고정한다. 같은 입력 재시도에는 같은 키를 쓰며 입력/버전 변경은 새 작업으로 처리한다. 응답 유실과 확정 실패를 구분하고 모든 저장·삭제를 일괄 자동 재시도하지 않는다.
- UTC 시점·지점 현지 날짜·IANA 시간대, PATCH 누락/null과 난이도 안정 키를 보존한다. 표시 이름·색상·브라우저 시간대를 원본 식별자나 지점 날짜의 근거로 대신 쓰지 않는다.

HTTP 전송·오류·헤더·멱등성의 상세 규칙은 [계약 규칙](../../packages/contracts/conventions.md)이 원본이다.

### 관리자 인증

관리자 세션은 모바일 Bearer 세션과 별개다. 브라우저는 서버가 발급한 HttpOnly cookie를 사용하며 access/refresh token을 localStorage나 Query 캐시에 저장하는 모바일 인증 흐름을 만들지 않는다. 세션 조회에서 받은 CSRF 값을 계약에 지정된 관리자 쓰기 요청에 전달하고 credentials·Origin·cookie 경로 조건을 유지한다.

cookie·CSRF·Origin과 만료 기준은 [C02](../../packages/contracts/conventions.md#인증기기관리자--c02c03c09)를 따른다. UI에서 버튼을 숨기는 것으로 서버 권한 검사를 대신하지 않는다. 세션 종료·계정 변경 뒤 늦은 조회·저장 결과가 새 세션에 반영되지 않게 세션 세대를 검사한다. 인증 만료를 빈 데이터나 저장 성공으로 표시하지 않으며 재인증·입력 보존의 구체 동작은 004 계획에서 연결한다.

개발 proxy는 개발 편의를 위한 것이다. 기존 proxy가 Origin·cookie를 변경하지 않는 기준을 유지하고 Secure cookie를 약화해 로컬 HTTP에서 인증을 통과시키지 않는다. 관리자 인증의 로컬 HTTPS·CSRF와 실제 브라우저 검사는 004에서 수행한다.

## 의존 방향과 공개 진입점

| 경계 | 규칙 |
|---|---|
| 앱 밖 | contracts 공개 export만 소비. server/mobile 소스와 계약 내부 generated 경로를 직접 import하지 않음 |
| 브라우저/Node | `src/`에 Node 설정·DB·서버 비밀을 가져오지 않음. Vite 설정과 node-checks의 환경을 분리 |
| 화면과 전송 | 화면/훅이 API를 호출. API·순수 유틸·공용 UI가 화면·Provider를 역참조하지 않음 |
| 공용 변경 | 계약·root 설정·lockfile은 지정 담당이 갱신. 생성물과 dist는 직접 수정하지 않음 |
| 개발 자료 | 합성 fixture·health 진단은 검사 전용. 제품 기능이 개발용 자료에 의존하지 않음 |

런타임 패키지는 admin workspace에 직접 선언하고 설치는 루트의 단일 lockfile로 관리한다. 브라우저 공개 설정은 별도로 정의하며 `ADMIN_DEV_API_ORIGIN` 등 Node 전용 proxy 값을 제품 번들에 넣지 않는다. 현재 lint가 모든 폴더 의존 규칙을 강제하는 것은 아니므로 도입 시 리뷰·자동 검사 범위를 정한다.

## 명명 규칙

React 컴포넌트는 `BrandForm.tsx`처럼 PascalCase, 훅은 `useSaveBrand.ts`, 일반 함수 파일은 `brandInput.ts`처럼 역할을 이름에 드러낸다. 화면 타입은 사용하는 코드 가까이 두고 실제 공유할 때 `types/`로 옮긴다. 순수 유틸은 `lib/`에 두며 `utils/`와 중복 분류하지 않는다. 현재 상대 import를 유지하고 alias 도입 시 TypeScript·Vite·Node 검사에서 모두 해석되는지 확인한다. 함수 설명은 [프로젝트 주석 규칙](../work-rules.md#코드-주석)을 따른다.

## 상태 관리

| 상태 | 소유와 수명 |
|---|---|
| 서버 조회 결과 | 조회 훅/서버 캐시. 관리자 세션·자료 종류·대상·필터·페이지를 구분하며 별도 전역 store에 복제하지 않음 |
| 관리자 세션 | 인증 Provider의 준비/인증 상태. cookie 원문을 읽거나 저장하지 않음 |
| 저장 전 입력 | 각 폼의 독립 draft. 최신 서버 원본·version과 분리하고 자동 재조회로 덮어쓰지 않음 |
| 펼침·선택·확인창 | 해당 화면/부품의 React 상태. 여러 화면 공유 필요가 생길 때만 승격 |
| 이미지 준비·업로드 | C08 이미지 draft와 파일별 처리 상태. 폼 저장과 이미지 bytes 완료를 구분 |

A02의 브랜드 폼과 암장 폼은 draft·대상·version·저장 중 상태를 각각 관리한다. 한쪽 저장·항목 전환으로 반대쪽 입력을 초기화하거나 함께 저장하지 않는다. 다른 항목 불러오기·나가기는 해당 변경의 계속 작성/나가기 확인을 거친다. 화면 전체를 떠날 때는 남아 있는 두 폼의 변경을 함께 고려한다. 상세 결과는 [독립 폼 원본](../admin-spec.md#브랜드암장-저장과-입력-유지)을 따른다.

실패·충돌에서는 입력을 유지하고 성공한 변경만 서버 원본으로 갱신한다. mutation 완료가 다른 항목이나 새 세션의 폼을 초기화하지 않도록 요청 당시 대상과 현재 대상/세션을 확인한다. 권한 상실 시 보호 자료를 회수하며 재인증 전 draft를 다른 관리자에게 표시하거나 자동 전송하지 않는다. draft의 영속 저장은 기본 적용하지 않는다.

난이도 삭제는 과거 키·개수 보존, 기존 암장 벽은 읽기 전용이라는 기준을 유지한다. 신규 행만 새 키 요청으로 구분하고 이름·순서 변경으로 기존 키를 재발급하지 않는다. 세팅 날짜와 공지 저장/삭제도 각 원본의 확인·취소·실패 결과를 따른다.

로고·공지 이미지는 [C08](../../packages/contracts/conventions.md#파일업로드이력작업--c08c11)의 image-draft→업로드→폼 참조 절차로 준비한다. 파일 선택·미리보기만으로 저장 성공을 표시하지 않고 실패·취소 시 기존 참조를 유지한다. 대기 중 업로드·임시 이미지 정리와 서버 확정 참조의 경계는 006·019 계획에서 정한다.

캐시 도입 시 저장·삭제에 영향받는 목록·상세·선택 자료의 키를 기능별로 정한다. 브랜드 변경 후 암장 폼을 갱신해도 저장 전 입력을 덮어쓰지 않는다. 브라우저 복귀·네트워크 회복 시 재조회와 충돌 처리를 검증하고 자료 갱신을 자동 폼 초기화로 구현하지 않는다.

## 검증 방법

명령과 수행 범위는 [개발 안내](../development.md#실행과-완료-확인)를 따른다. admin 변경은 workspace lint·typecheck·test·build, 문서 변경은 문서 검사, 공용 설정·계약 변경은 영향받는 공통 검사를 수행한다.

| 검사 | 확인할 결과 |
|---|---|
| 정적·단위 | 계약 소비·날짜/null/키 변환·독립 폼 상태·오류 매핑 |
| 합성 응답 UI | 각각 저장·불러오기·취소·실패·충돌·늦은 응답·반대쪽 입력 유지 |
| 실제 브라우저/인증 | HTTPS·Secure cookie·CSRF·Origin·만료/로그아웃·다른 세션의 자료 회수 |
| 실제 API/DB 연동 | 관리자 허용과 일반 회원/크루 관리자 거절·중복 저장 방지·과거 난이도 보존·이미지 참조 |
| 화면 확인 | A02·A03·A04 최신 시안·키보드 이동·라벨·포커스·확인창·입력 유지 |

현재 Node 기반 test와 빌드 성공은 제품 폼·인증·실제 연동 완료를 증명하지 않는다. UI 검사 도구·라우트 구성·상태 도구와 실제 FR별 사례는 004·006·019 계획에서 정하며 실행하지 않은 검사는 미수행으로 남긴다.
