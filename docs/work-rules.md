# 프로젝트 작업 규칙

## 기준 자료

현재 제작한 최신 Figma 화면과 사용자가 확정한 동작을 기준으로 삼는다. 예전 문서나 생성 이미지에 맞추려고 최신 화면을 되돌리지 않는다. 화면에 보이지 않는 저장·권한·계산 규칙은 기능 명세와 기록 관계 설계를 따른다.

- 제품 범위는 [PRD](prd.md), 기능은 [기능 명세](functional-spec.md), 기술 구성은 [기술·운영 명세](technical-spec.md)에서 확인한다.
- UI는 [화면 설계](screen-design.md)와 [현재 시안](screens.md)을 확인한다. Figma 제작·수정 전에 [디자인 시스템 규칙](figma-design-system.md)을 반드시 읽는다.
- 새로운 화면·상태·안내 문구를 임의로 추가하지 않는다. 현재 범위와 필요한 추가 적용은 [화면 번호표](screen-numbering.md)·[작업 목록](screen-worklist.md)을 따른다.
- 작성·제작·구현·검증 여부를 구분한다. 실제 수행하지 않은 작업을 완료로 표시하지 않는다.

## 에이전트 개발

기능 개발·변경은 [Spec Kit 개발 흐름](development-workflow.md)을 따른다. 사용자가 스킬을 직접 명시하지 않아도 관련 설치 스킬을 읽고 현재 단계부터 진행한다. Living Spec 원칙과 원본 위치는 [프로젝트 원칙](../.specify/memory/constitution.md)·[스펙 목록](../specs/README.md)을 따른다.

## 코드 주석

- 새로 작성하거나 변경하는 함수에는 역할을 설명하는 주석을 남긴다. JavaScript·TypeScript 함수는 JSDoc 형식을 사용하고, 공개 함수에는 입력·반환값·실패 조건과 중요한 부작용을 설명한다.
- 복잡한 로직·검증 경계·예외 처리에는 해당 선택의 이유와 제약을 설명한다. 코드의 동작을 그대로 반복하는 주석은 피한다.
- 구현을 변경할 때 관련 주석도 함께 갱신한다. 생성물의 주석은 생성 도구에서 관리하며 생성 파일을 수기로 수정하지 않는다.
- 리뷰에서 docstring coverage 경고를 확인하고 누락된 함수 설명을 보완한다. 수치를 채우기 위한 내용 없는 주석을 추가하지 않는다.

## 문서 관리

| 문서·위치 | 관리할 내용 |
|---|---|
| 루트 README | 프로젝트 소개·현재 단계·개발 시작 링크 |
| AGENTS.md | 작업별 필수 규칙과 기준 문서를 찾는 목차 |
| docs/README.md | 문서 위치와 각 문서의 역할 |
| 현재 명세 | 현재 적용할 기능·화면·기술 규칙 |
| 준비·작업 목록 | 아직 해야 할 작업과 보류 항목 |
| docs/history/ | 결정 이유·대안·과거 계획·제작·검증 기록 |
| docs/figma/ | 현재 Figma 노드·공통 부품 자료·화면 사진 |

- 세부 규칙은 기준 문서 한곳에서 관리한다. 다른 문서에는 필요한 짧은 요약과 링크만 둔다. 화면별 권한 요약·검증 시나리오처럼 그 자리에서 필요한 반복은 유지한다.
- 결정되면 현재 명세를 직접 고친다. 날짜별 후속 설명을 계속 붙이지 않는다. 이유·대안이 필요하면 기록 폴더에 별도로 남기고 기준 문서로 연결한다.
- 기록 폴더의 과거 제안·완료 상태를 현재 요구사항으로 사용하지 않는다. 기록 전체를 매 작업의 필수 읽기 대상으로 넣지 않는다.
- 개인 응답 언어·말투 같은 취향은 사용자 로컬 설정에서 관리한다. 프로젝트 문서에 복사하거나 사용자 로컬 파일을 프로젝트에서 참조하지 않는다.
- 기능·정책 ID(F·S·D·B·T)와 화면 번호·고정 주소는 유지한다. 파일을 옮기면 연결 문서·검수 페이지의 링크도 함께 고친다.
- 문서를 수정한 뒤 `python3 scripts/check-docs.py`로 링크·JSON 문법·화면 번호와 상태 자료의 일치를 확인한다. 기능 동작 검증을 대신하는 검사는 아니다.

정리 방식의 근거와 이전 작업 기록은 [기록 안내](history/README.md)에서 찾는다.
