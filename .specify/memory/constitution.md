# Holdlog Constitution

## Core Principles

### I. Living Spec을 개발 기준으로 유지

기능 개발은 관련 스펙에서 시작한다. 제품 동작을 변경할 때 기존 `spec.md`를 먼저 갱신하고 설계·작업·코드·검증을 맞춘다. 같은 기능의 후속 변경마다 새 스펙을 만들지 않는다. 구현 방법만 바뀌면 제품 동작을 유지한 채 계획과 코드를 수정한다. 상세 운영은 [개발 흐름](../../docs/development-workflow.md)을 따른다.

### II. 원본 한곳과 기존 연결 보존

각 요구사항의 상세 원본은 한곳에서 관리한다. 기능 스펙은 공통 규칙과 화면 자료를 참조하며 복사해 별도 원본으로 만들지 않는다. 상세 규칙을 옮기면 기존 위치는 요약·링크로 바꾸고 S·D·B·T 번호와 화면 주소를 보존한다. 자료의 우선순위와 문서 역할은 [프로젝트 작업 규칙](../../docs/work-rules.md)을 따른다.

### III. 확정한 범위 안에서 구현

사용자가 확정한 기능·화면·상태·문구를 기준으로 한다. 에이전트는 새 제품 동작을 임의로 추가하지 않는다. 기존 자료와 요청에서 판단할 수 있는 구현 선택은 진행하고, 사용자 결정이 필요한 제품 변경만 확인한다. 보류 항목은 [미결정 사항](../../docs/open-questions.md)에서 확인한다.

### IV. 계약에 따른 협업

앱·서버·관리자 웹이 주고받는 입력·결과·권한·오류·재요청 동작을 구현 전에 정한다. 담당자와 에이전트는 동일한 계약 원본을 사용한다. 스펙의 요구사항과 작업·검증의 연결을 기록해 누락과 임의 기능 추가를 확인한다. 독립 작업은 파일 충돌을 피하도록 나누고 합친 뒤 실제 연동을 확인한다.

### V. 실제 증거로 완료 판단

관련 테스트·타입 검사·빌드·연동·시안 비교를 작업에 맞게 수행한다. 연결·권한·삭제·시간대·집계는 정상 동작과 거절 조건을 확인한다. 단순 수정에 구현을 그대로 따라 쓰는 테스트를 추가하지 않는다. 작성·검토·구현·실행 검증 상태를 구분하며 실행하지 않은 검사를 통과로 표시하지 않는다.

## 기준 자료와 제약

기술 선택은 [기술·운영 명세](../../docs/technical-spec.md), 기능은 [기능 명세](../../docs/functional-spec.md), UI는 [화면 설계](../../docs/screen-design.md)를 따른다. 기능별 스펙이 도입된 범위의 원본 위치는 [스펙 목록](../../specs/README.md)에서 찾는다. 개인 응답 언어·말투는 프로젝트 원칙에 복사하지 않는다.

## Development Workflow

사용자는 결과를 요청하고 에이전트는 현재 단계에 맞는 설치된 Spec Kit 스킬을 선택한다. 관련 스킬을 읽고 명세·설계·작업·검사의 산출물을 실제로 작성한다. 단계 전환마다 불필요한 재승인을 요구하지 않는다. 체크리스트의 통과는 명세 품질 확인이며 구현 완료가 아니다. 현재 작업은 관련 스펙을 선택해 실행하고 개발 과정은 [기록 폴더](../../docs/history/README.md)로 구분한다.

## Governance

이 원칙은 사용자가 승인한 개발 운영 방식을 정의한다. 사용자의 최신 명시적 지시가 우선한다. 원칙을 바꾸면 이유·영향을 확인하고 버전·갱신일을 수정한다. 호환되지 않는 변경은 주 버전, 원칙 추가는 부 버전, 표현 보완은 수정 버전을 올린다. 현재 원칙과 중요한 결정 이유를 구분하고 실제 완료 상태를 검토한다.
