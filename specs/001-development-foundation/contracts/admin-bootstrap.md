# 초기 서비스 관리자 준비 절차

이 문서는 [#8](https://github.com/trycatch98/Holdlog/issues/8)의 001/T016 결과다. 비밀 입력·전달·Argon2id 해시·최초 생성·명시적 교체·재실행·실패 처리 절차를 004에 전달한다. 절차 검토를 수행했으며 실제 계정 생성이나 인증 실행 결과는 아니다.

## 기준과 실행 조건

인증 동작의 원본은 [C02 사용 규칙](../../../packages/contracts/conventions.md#인증기기관리자--c02c03c09), 저장 대상은 [ServiceAdministrator·AdminSession 모델](../../002-shared-contracts/data-model.md#2-계정기기크루--c02c03), 실제 구현·검증은 [004 계정·인증 FR-006](../../004-identity-profile/spec.md)이다. loginId·credentialHash·active·version의 필드와 HTTP 입력은 원본을 따른다.

실제 실행은 004가 관리자 저장 구조·해시 생성/검증·초기 준비 도구를 구현하고 검증한 뒤 가능하다. 현재 실행 가능한 bootstrap 명령은 없다. 공개 관리자 가입 API나 별도 제품 화면을 만들지 않으며 일반 회원·크루 관리자 역할을 서비스 관리자 권한으로 변환하지 않는다.

## 비밀 입력과 전달

1. 실행 담당자는 개발/시험 환경과 대상 DB를 확인한다. 운영 DB나 운영 계정 자료를 로컬 시험에 복사하지 않는다. 대상 환경이 불명확하거나 DB 설정이 누락되면 입력 전에 중단한다.
2. 관리자 식별자와 새 비밀번호를 별도로 준비한다. 비밀번호는 다른 계정과 재사용하지 않는 무작위 비밀로 생성하고 담당자만 접근할 수 있는 비밀 보관소에 둔다. 식별자·입력값은 C02의 입력 제약으로 검사한다.
3. 비밀번호 입력은 echo가 꺼진 대화형 입력 또는 제한된 접근 권한의 비밀 입력 채널을 사용한다. 명령 인수·셸 이력·공유 .env 예시·Git·이슈·PR·검증 기록에 비밀번호를 넣지 않는다. 모바일 EXPO_PUBLIC_*·웹 VITE_* 변수와 앱 빌드에는 전달하지 않는다.
4. 초기 비밀은 지정한 수신자만 접근할 수 있는 비밀 보관소의 공유 기능 또는 접근 제한된 별도 채널로 전달한다. 공개 링크·공개 채팅·이메일 본문에 원문을 남기지 않는다. 전달 기록에는 대상 환경·작업 종류·시각·담당자·성공/실패만 남기며 원문이나 해시를 포함하지 않는다.
5. 수신자의 수령을 확인하고 임시 입력 파일·불필요한 사본을 제거한다. DB에 원문을 저장하지 않는다. 전달 실패 시 성공으로 표시하지 않고 접근을 제한한 상태로 재전달하거나 아래 교체 절차를 수행한다.

## Argon2id와 최초 생성

004의 준비 도구는 새 비밀번호마다 암호학적으로 안전한 새 salt로 Argon2id 해시를 생성하고, salt·알고리즘·파라미터를 포함한 검증 가능한 인코딩을 credentialHash에 저장한다. 일반 SHA 해시나 고정 salt로 대체하지 않는다. 해시 파라미터·라이브러리 버전은 004 설계에서 실행 환경의 비용을 검증한 뒤 고정하며 본 문서에서 별도 계약으로 복사하지 않는다. 알고리즘 근거는 [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)이다.

최초 생성은 create-only 작업이다. 대상 환경·입력을 검사하고 해시 생성에 성공한 후, loginId의 unique 제약을 이용해 저장한다. 동일 loginId가 이미 존재하면 생성을 거절하고 기존 credentialHash·active·version을 유지한다. 조회와 저장 사이에 다른 실행이 생성해도 같은 원칙을 지킨다. 기존 값을 UPDATE하는 upsert를 최초 생성 경로에 사용하지 않는다.

저장과 필요한 결과 기록은 004의 트랜잭션 경계에 맞춰 수행한다. 해시 실패·DB 실패·동시 생성 충돌에서는 비정상 종료하고 기존 자료를 변경하지 않는다. 성공 메시지에는 비밀번호·해시·DB 주소·접속 비밀을 출력하지 않는다.

## 명시적 비밀번호 교체

교체는 최초 생성과 구분된 명시적 작업으로 구현한다. 실행 담당자는 환경·대상 principal·교체 의도를 확인하고 새 비밀을 위 입력 절차로 전달한다. 대상을 찾을 수 없으면 교체 경로에서 새 계정을 만들지 않는다. 비활성 계정을 비밀번호 교체만으로 활성화하거나 식별자·권한을 바꾸지 않는다.

저장 직전 대상의 현재 상태와 기대 version을 확인하고, 새 Argon2id 해시와 version 변경을 원자적으로 반영한다. 동시 교체 충돌은 실패로 반환하고 최신 상태를 다시 확인한 뒤 재실행한다. 실패 시 기존 비밀번호를 유지하며 성공으로 안내하지 않는다. 교체 시 기존 관리자 세션 처리 방식은 004에서 C02의 인증 회수 설계와 함께 확정·검증해야 하며, 이 절차만으로 기존 세션 회수를 수행했다고 표시하지 않는다.

## 재실행과 실패 복구

| 상황 | 처리와 보존할 결과 |
|---|---|
| 입력·필수 설정 누락/형식 오류 | 해당 입력 또는 설정 이름만 알리고 실패. 원문·접속 문자열은 출력하지 않음 |
| 기존 loginId로 최초 생성 재실행 | 이미 존재함을 알리고 실패. 기존 비밀번호·활성 상태·버전 유지. 변경하려면 명시적 교체 작업 사용 |
| Argon2id 생성 실패 | 저장 전에 중단. 기존 자료 유지. 원시 예외나 입력을 기록하지 않음 |
| DB 접근/저장 실패 | rollback 후 실패. 비밀이 없는 실패 분류와 작업 결과만 기록 |
| 동시 생성·교체 충돌 | unique/version 검사로 한 변경만 반영. 나머지는 실패 후 현재 상태 재확인 |
| commit 후 응답 유실 | 성공 여부가 불명확함을 기록. 같은 create-only 재실행으로 비밀번호를 덮어쓰지 않음. 저장 결과 확인 후 새 비밀이 필요하면 명시적 교체 |
| 비밀 전달 실패 | 계정 생성과 전달 상태를 구분. 무조건 재생성하지 않고 접근 제한 채널로 재전달 또는 명시적 교체 |

검증 기록은 합성 자료와 성공/실패·미수행 여부만 포함한다. 기존 계정 삭제나 DB 볼륨 제거를 복구 수단으로 사용하지 않는다.

## 004에 전달할 검증 조건

- 합성 최초 생성 후 Argon2id 검증이 성공하고 원문이 저장·로그·공개 설정·번들에 없는지 확인한다.
- 동일 loginId로 재실행·동시 생성해 기존 credentialHash·active·version이 바뀌지 않는지 확인한다.
- 명시적 교체 성공 시 새 비밀로 검증되고 이전 비밀로 거절되는지 확인한다. 없는 대상·버전 충돌·해시/DB 실패는 기존 상태를 보존해야 한다.
- 실패 출력과 결과 기록에 원문·해시·DB 접속 비밀이 포함되지 않는지 합성 비밀 표식으로 검사한다.
- 실제 관리자 로그인·보호 API 허용/거절·관리자 세션과 모바일 세션 분리·로컬 HTTPS의 Secure cookie·CSRF·Origin 검사는 004에서 수행한다. 교체와 기존 세션 회수의 관계도 같은 설계에서 검증한다.

001/T016 완료는 위 절차의 작성과 C02·004 전달 조건 대조다. 실제 principal 저장·로그인·교체 실행·cookie/CSRF 검사는 미수행이며 001 완료 조건으로 당겨오지 않는다.
