# 프론트·백엔드 작업 구분

프론트 개발자와 백엔드 개발자는 서로 다른 사람이다. 프론트는 모바일과 관리자 웹에서 사용자가 보는 화면·입력·조작·기기 동작을 맡는다. 백엔드는 API·DB·권한·계산·파일 저장·비동기 작업을 맡는다. 모바일과 관리자 웹을 각각 다른 프론트 담당자에게 배정해도 같은 기준을 사용한다.

이 문서는 **개발자별 담당 범위와 주고받을 결과의 원본**이다. 기능 동작은 각 [기능 스펙](README.md)과 연결한 기존 명세, 계약 소비 범위·변경 책임은 [공통 계약 설계 범위](002-shared-contracts/contract-scope.md)에서 관리한다. 기능마다 프론트용·백엔드용 제품 스펙을 따로 만들어 상세 규칙을 복사하지 않는다.

## 공통 책임과 변경 방식

| 대상 | 프론트 책임 | 백엔드 책임 | 함께 확인할 것 |
|---|---|---|---|
| 기능 요구사항 | 원본 화면·입력·진입·표시 결과 확인 | 원본 저장·권한·연결·계산·삭제 결과 확인 | 같은 `spec.md`의 FR별 검증 표를 사용. 제품 동작 변경은 원본부터 수정 |
| 공통 계약 | 화면에 필요한 입력·결과·실패 항목을 제시하고 소비 결과 확인 | 모델·권한·처리 경계를 반영한 계약 초안 작성 | 양쪽이 같은 버전과 정상/실패/충돌/재요청 예제를 확인한 뒤 계약 확정 |
| 공통 화면 부품 | 003 담당이 모바일 부품·이동·입력 유지 관리. 관리자 웹 공통 부품은 해당 프론트 담당이 관리 | 공통 응답·실패 분류 제공 | 기존 시안과 계약의 표현 일치. 클라이언트 검사로 서버 검사를 대신하지 않음 |
| 데이터와 업무 처리 | 계약대로 요청하고 결과·실패·충돌을 표시 | 저장·접근 허용/거절·수치 계산·같이 저장할 변경·작업 등록의 최종 판단 | 프론트가 화면 표시용 권한을 판단해도 최종 권한 검사는 서버에서 수행 |
| 기기 기능 | 로그인 SDK·지도·권한·QR·푸시 수신·영상 재생·운동 알림 등 앱 연동 | 인증 검증·암장 자료·초대 검사·푸시 발송·미디어 전달 등 서버 지원 | 실제 기기와 실제 서버를 연결해 성공·거절·복귀 확인 |
| 공통 파일 | 자신의 앱/웹 영역 변경을 담당 | 자신의 서버/DB/작업 처리 영역 변경을 담당 | `packages/contracts`, 루트 설정, 공유 문서는 건별 한 명을 변경 담당으로 지정. 다른 담당이 동시에 덮어쓰지 않음 |

계약을 먼저 구현하는 사람이 계약을 혼자 확정하지 않는다. C번호의 기능 주 책임은 계약 변경을 모으는 범위이며 자동으로 사람의 이름이나 최종 제품 결정 권한을 뜻하지 않는다. 담당자가 계약 변경을 요청하면 영향받는 프론트·백엔드가 원본과 소비 결과를 확인한다.

## 여러 개발자의 작업 배정

스펙 하나에 개발자 한 명을 고정하지 않는다. 상위 이슈에는 스펙의 누락·선행 관계·최종 완료 확인을 챙길 기능 책임자를 두고, 독립적으로 개발·검토 가능한 서브 작업마다 주 담당자 한 명을 GitHub Assignees로 배정한다. 기본 PR 리뷰는 CodeRabbit이며, 추가 사람 검토가 필요한 경우 PR Reviewers로 요청한다. 책임자가 모든 코드를 작성하는 것은 아니다. 사람이 지정되지 않았으면 임의 계정을 배정하지 않고 역할만 정해 둔다.

| 역할 라벨 | 맡을 결과 |
|---|---|
| `role:frontend` | 화면·입력·탐색·기기 동작·API 소비 |
| `role:backend` | API·DB·권한·계산·파일·서버 작업 |
| `role:shared` | 여러 개발자가 소비할 계약·공통 부품·공용 설정의 준비·변경 |
| `role:integration` | 합친 결과·실제 연동·스펙 최종 완료 확인 |

작업 이슈에는 주 역할 하나를 둔다. 프론트와 백엔드가 모두 구현해야 하는 큰 작업은 역할별 결과로 나누며, 공통·연동 작업에도 실제 주 담당자는 한 명을 정한다. 추가 사람 검토자는 PR Reviewers로 요청하고 필요한 협업 범위를 작업에 적는다. 역할은 사람의 직함을 제한하지 않으며 한 사람이 여러 역할의 서로 다른 작업을 맡을 수 있다.

모바일·관리자 웹·API·계약 등 실제 변경 영역과 변경할 파일/폴더를 작업마다 적는다. 여러 프론트 개발자는 작성·상세·조회처럼 독립 결과로 나눌 수 있지만, 화면 수만으로 나누지 않고 공통 코드 변경 범위를 함께 확인한다. 여러 작업이 같은 계약·탐색·공통 부품·루트 설정을 수정하면 공통 변경 작업과 담당을 먼저 정하고 그 결과를 소비한다. 불가피한 공동 변경은 한 담당이 모으며 코드 리뷰 담당이 파일의 독점 수정권을 뜻하지는 않는다.

작업 가져오기·상태·이슈 생성·완료 처리 절차는 [GitHub 개발 흐름](../docs/development-workflow.md#github-이슈와-pr)에서만 관리한다. 작업별 브랜치·별도 작업 폴더로 실행하고 공유 Spec Kit 선택 파일과 공통 진행 기록을 여러 작업자가 동시에 덮어쓰지 않는다.

## 계약을 주고받는 순서

1. 같은 기능 스펙의 FR별 검증 표와 원본을 양쪽이 확인한다. 아직 합의하지 않은 제품 동작은 계약으로 고정하지 않는다.
2. 백엔드는 저장·권한·처리 경계를 포함한 계약 초안을 작성하고 프론트는 화면·기기에서 소비할 수 있는지 검토한다. 양쪽이 정상·빈 결과·실패·권한 거절·동시 수정·같은 요청 재시도의 예제를 대조한다.
3. 계약 원본·버전과 변경 담당을 지정하고 확정된 범위에 한해 개발을 시작한다. 서버 구현이 없어도 프론트는 같은 계약의 예제 응답으로 독립 개발할 수 있다. 백엔드는 같은 요청·기대 결과로 API를 검사한다.
4. 계약 변경이 필요하면 소비자와 영향받는 FR을 먼저 찾는다. 담당 한 명이 공통 원본을 고치고 양쪽이 자료형·입력·예제와 필요한 계획/작업을 함께 갱신한다. 새 필드·오류 결과를 한쪽에서만 추가하지 않는다.
5. 기능별 실제 서버가 준비되면 프론트의 예제 응답을 실제 API로 연결하고 같은 FR별 상황을 다시 검사한다. 실제 기기가 필요한 항목도 함께 확인한다.

계약의 구체 필드·세션 방식·주소·파일 구조는 [002 API·데이터 계약 설계](002-shared-contracts/contracts/README.md)에서 관리한다. 이 문서에는 복사하지 않는다. 공통 예제의 입력과 기대 결과를 프론트용·백엔드용으로 따로 작성하지 않는다.

## 기능별 전달 자료와 완료 상태

후속 기능의 `plan.md`·`tasks.md`에서는 하나의 기능 안에 `[FE]`, `[BE]`, `[SHARED]`, `[INTEGRATION]` 작업 표시와 담당 역할을 둔다. 이는 작업 구분이며 별도 제품 스펙을 생성하라는 뜻이 아니다. 같은 FR과 계약 원본을 참조하며 작업별 변경 파일·선행 계약·검사·전달 결과를 기록한다. 실제 문서는 해당 단계에서 작성한다.

| 상태 | 남길 증거 | 완료로 볼 수 있는 범위 |
|---|---|---|
| 계약 합의 | 계약 원본/버전·양쪽 검토·공통 예제·미정/보류 범위 | 해당 범위의 독립 개발 착수 가능 |
| 프론트 단독 확인 | 소비 계약 버전·검사한 FR·시안 비교·예제/실제 API 사용 구분·기기 검사 여부 | 화면과 소비 동작 확인. 백엔드와 합친 기능 완료는 아님 |
| 백엔드 단독 확인 | 제공 계약 버전·검사한 FR·API/DB/권한/계산/작업 결과 | 서버 동작 확인. 화면과 합친 기능 완료는 아님 |
| 실제 연동 확인 | 같은 계약 버전의 앱/웹/서버·FR별 성공/거절/충돌/재요청·자료 보존/회수·실기기/미수행 기록 | 원본과 스펙의 필수 결과를 모두 만족한 기능만 완료 |

앞선 단독 검사 결과가 합친 뒤에도 맞는지 양쪽이 함께 확인한다. 발견한 문제가 화면 처리인지 서버 결과인지 계약 자체인지 구분하고 해당 담당이 수정한다. 계약 원본이 바뀌면 양쪽 검사와 관련 연동 검사를 다시 맞춘다. 실제 개발자 이름과 공통 변경 담당은 작업 배정 때 정하며 현재 작성으로 배정·합의·실행 완료를 표시하지 않는다.

001 기반의 실제 소비자 대조와 후속 전달은 [T024 계약·예제 소비 기록](../docs/history/development/001-foundation-verification.md#공통-계약예제-소비-대조)·[T030 별도 폴더 재현 기록](../docs/history/development/001-foundation-verification.md#별도-폴더-재현과-비밀-경계--11--t027t030)·[002의003/004/006 전달 안내](002-shared-contracts/quickstart.md#후속003004006-전달)를 따른다. 검사 결과·도구 목록·해시는 해당 원본에서만 관리한다.
