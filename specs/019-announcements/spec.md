## User Scenarios & Testing

### User Story 1 - 앱 시작 공지·관리자 공지 관리 이용 (Priority: P1)

사용자 또는 개발 담당자는 아래 기능을 해당 원본의 조건으로 이용한다.

**Why this priority**: 이 개발 단위의 핵심 결과이며 후속 기능이 같은 자료를 사용할 기준이다.

**Independent Test**: 필요한 선행 자료를 공통 계약의 예제로 준비하고 요구사항별 검증 표의 상황과 원본 기대 결과를 비교한다. 예제 검사는 실제 서비스 연동 완료와 구분한다.

**Acceptance Scenarios**:

아래 [요구사항별 검증 연결](#요구사항별-검증-연결)의 각 행이 이 흐름의 수락 기준이다. 해당 상황에서 작업한 결과를 행에 지정한 원본 기대 결과와 비교한다.

### User Story 2 - 실패와 경계에서 자료 유지 (Priority: P1)

사용자는 실패·거절·동시 요청을 성공으로 오인하지 않고 기존 자료와 입력을 원본 기준으로 유지할 수 있다.

**Why this priority**: 정상 결과뿐 아니라 권한과 자료 보존이 기능 완료의 조건이다.

**Independent Test**: 각 FR의 해당 거절 조건과 아래 경계 사례를 준비해 저장 결과·조회 결과·화면 상태를 비교한다.

**Acceptance Scenarios**:

1. **Given** 작업 조건 또는 권한이 충족되지 않음, **When** 대상 작업을 요청함, **Then** 허용되지 않은 변경·조회가 발생하지 않고 기존 원본의 실패 결과를 따른다.
2. **Given** 저장 실패·중복 요청·동시 변경에 해당하는 상황, **When** 해당 작업을 재요청하거나 다시 조회함, **Then** 원본 기준의 자료 보존·중복 방지·충돌 결과를 확인할 수 있다.

### 대표 확인 사례

1. **Given** 공지 목록을 조회할 수 있고 기기 당일 숨김이 없음, **When** 앱을 새로 켜고 이미지를 넘긴 뒤 닫음, **Then** 목록 순서대로 표시되고 단순 화면 복귀에서는 다시 열리지 않는다.
2. **Given** 기기에서 오늘 그만보기를 선택함, **When** 같은 날 계정을 바꾸고 공지 목록도 바뀜, **Then** 해당 기기의 당일 숨김은 유지되고 다른 기기의 선택은 바꾸지 않는다.

대표 사례는 검증을 위한 짧은 요약이며 상세 규칙은 범위 표의 원본에서 관리한다.

### Edge Cases

- 목록0·1·3개·자정·계정 변경·다른 기기·스와이프와 링크 클릭·삭제 취소·저장 실패를 구분한다.
- 공통 상태·실패·입력 보존은 [기능 명세2.1절](../../docs/functional-spec.md#21-상태와-입력)을 참조한다. 별도 상태 시안을 임의로 추가하지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 사용자는 앱 시작 공지 이미지를 순서대로 직접 넘기고 이미지별 링크를 열거나 팝업을 닫을 수 있어야 한다.
- **FR-002**: 오늘 그만보기는 기기의 당일 공지 전체에 적용하고 계정·공지 변경으로 해제하지 않아야 한다.
- **FR-003**: 공지 없음·조회 실패·링크 실패는 로그인·초대·기본 앱 이용을 막지 않아야 한다.
- **FR-004**: 서비스 관리자는 공지 이미지·링크·순서를 등록·수정하고 확인 후 삭제할 수 있어야 한다.

### 요구사항별 검증 연결

각 행의 상황을 확인하고 연결한 원본의 기대 결과를 따른다. 상세 규칙·계산식은 복사하지 않는다. T번호가 없는 항목은 해당 원본 절의 검증·완료 기준과 규정된 동작을 직접 검사한다. 프론트·백엔드 단독 검사와 실제 연동 검사에 같은 행을 사용하며 아직 실행한 결과는 없다.

| 요구사항 | 검사할 상황 | 기대 결과 원본·검증 항목 |
|---|---|---|
| FR-001 | 공지0/1/3개·수동 넘김·이미지별 링크·닫기·단순복귀 미재표시 | [S26](../../docs/functional-spec.md#s26-앱-시작-공지-팝업) |
| FR-002 | 기기 당일 숨김·재시작/계정변경/공지변경·다음 날짜·다른 기기 | [S26](../../docs/functional-spec.md#s26-앱-시작-공지-팝업) |
| FR-003 | 공지없음/조회실패/링크실패에도 로그인·초대·앱이용 유지 | [S26](../../docs/functional-spec.md#s26-앱-시작-공지-팝업) |
| FR-004 | 관리자 공지 등록/수정/순서·삭제 성공/취소/실패·무권한 거절 | [공지 관리](../../docs/admin-spec.md#공지-관리) · [3. 완료 확인 기준](../../docs/admin-spec.md#3-완료-확인-기준) |

### Key Entities

- 공지 항목·이미지·이동 링크·순서·기기 당일 숨김. 상세 필드와 형식은002 공통 계약 설계에서 정하며 여기에는 복사하지 않는다.

## Success Criteria

### Measurable Outcomes

- **SC-001**: FR-001~FR-004에 연결한 정상 수락 시나리오가 모두 원본의 기대 결과와 일치한다.
- **SC-002**: 각 FR의 해당 실패·거절 조건과 경계 사례에서 금지된 변경·조회·중복 생성이0건이다.
- **SC-003**: 요구사항별 검증 표에 연결한 원본 검증과 후속 설계에서 구체화한 추가 사례를 모두 통과하고 미수행 결과를 완료로 표시하지 않는다.
- **SC-004**: 담당 화면·부품을 최신 시안과 대조하고 검토 대기·미정 범위를 완료로 표시하지 않는다.

## Assumptions

- 선행 관계의 원본은 [개발 단위 목록](../README.md#선행-관계)이다. 실제 연동 선행: [003 앱 탐색과 공통 화면 부품](../003-app-shell/spec.md), [004 계정·인증](../004-identity-profile/spec.md).
- 병렬 착수 전 필요한 계약: C02·C08·C12. 설계 범위와 완료 조건은 [계약 설계 범위](../002-shared-contracts/contract-scope.md)를 따른다. 계약 확정 후 예제로 독립 개발할 수 있으나 실제 완료는 선행 기능과 연동해 확인한다.
- 기존 검증 연결: [요구사항별 검증 표](#요구사항별-검증-연결)에 지정한 원본 절과 완료 기준. T번호의 기대 결과는 [원본 검증표](../../docs/functional-spec.md#9-기능-완료-확인-시나리오)에 두고 복사하지 않는다.
- 개발자별 담당·단독 검사·전달과 합친 뒤 완료 기준은 [프론트·백엔드 작업 구분](../development-roles.md)을 따른다.
- 현재 기능의 결과는 범위 명세와 품질 확인이다. 공통 형식은 [002 계약 설계](../002-shared-contracts/contracts/README.md)에 작성했으며, 기능별 구현 계획·작업 목록·앱 코드·실제 연동/실행 검증은 아직 없다.
