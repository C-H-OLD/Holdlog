## User Scenarios & Testing

### User Story 1 - 로그인과 내 정보·프로필 이용 (Priority: P1)

사용자 또는 개발 담당자는 아래 기능을 해당 원본의 조건으로 이용한다.

**Why this priority**: 이 개발 단위의 핵심 결과이며 후속 기능이 같은 자료를 사용할 기준이다.

**Independent Test**: 필요한 선행 자료를 공통 계약의 예제로 준비하고 요구사항별 검증 표의 상황과 원본 기대 결과를 비교한다. 예제 검사는 실제 서비스 연동 완료와 구분한다.

**Acceptance Scenarios**:

아래 [요구사항별 검증 연결](#요구사항별-검증-연결)의 각 행이 이 흐름의 수락 기준이다. 해당 상황에서 작업한 결과를 행에 지정한 원본 기대 결과와 비교한다.

### User Story 2 - 실패와 경계에서 자료 유지 (Priority: P1)

사용자는 실패·거절·동시 요청을 성공으로 오인하지 않고 기존 자료와 입력을 원본 기준으로 유지할 수 있다.

**Why this priority**: 정상 결과뿐 아니라 권한과 자료 보존이 기능 완료의 조건이다.

**Independent Test**: 각 FR의 해당 거절 조건과 아래 경계 사례를 준비해 저장 결과·조회 결과·화면 상태를 비교한다.

**Acceptance Scenarios**:

1. **Given** 작업 조건 또는 권한이 충족되지 않음, **When** 대상 작업을 요청함, **Then** 허용되지 않은 변경·조회가 발생하지 않고 기존 원본의 실패 결과를 따른다.
2. **Given** 저장 실패·중복 요청·동시 변경에 해당하는 상황, **When** 해당 작업을 재요청하거나 다시 조회함, **Then** 원본 기준의 자료 보존·중복 방지·충돌 결과를 확인할 수 있다.

### 대표 확인 사례

1. **Given** 로그아웃 상태에서 초대 링크로 진입함, **When** 로그인을 성공함, **Then** 유지된 초대의 가입 확인을 이어간다.
2. **Given** 가입 크루가 없는 기존 계정임, **When** 로그인함, **Then** 일정 안의 미가입 상태와 기존 본인 기록 접근을 함께 유지한다.

대표 사례는 검증을 위한 짧은 요약이며 상세 규칙은 범위 표의 원본에서 관리한다.

### Edge Cases

- 로그인 취소·만료·같은 이메일의 서로 다른 제공자·저장 실패·로그인 중 유지된 초대를 구분한다.
- 가입 증명으로 보호 API에 접근할 수 없다. 동일 provider/subject의 동시 가입은 계정 하나만 만들며 응답 유실은 재인증으로 기존 계정을 찾는다. 사진 실패로 가입을 되돌리거나 계정을 다시 만들지 않는다.
- 공통 상태·실패·입력 보존은 [기능 명세2.1절](../../docs/functional-spec.md#21-상태와-입력)을 참조한다. 별도 상태 시안을 임의로 추가하지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 사용자는 구글·Apple로 인증하고 기존 계정을 다시 사용할 수 있어야 한다. 신규 사용자는 SNS 인증 이후 별도 상세 정보 입력 단계를 거쳐 가입을 완료해야 한다. 이름은 필수이며 프로필 사진은 선택이다. 이름 입력 전에는 일반 회원 API 권한을 주지 않으며 이름 제출 성공 후에 계정을 생성한다. 화면은 확정07.02를 따른다.
- **FR-002**: 로그인 후 가입 크루 상태와 유지된 초대에 맞는 기존 화면으로 이동해야 한다.
- **FR-003**: 사용자는 내 정보와 로그인 계정을 조회하고 이름·프로필 사진을 수정할 수 있어야 한다.
- **FR-004**: 로그아웃은 해당 기기의 계정·푸시 연결을 해제하고 기록이나 크루 가입을 삭제하지 않아야 한다.
- **FR-005**: 프로필 화면은 계정 삭제를021 범위로 연결하고 직접 삭제 규칙을 별도로 만들지 않아야 한다.

- **FR-006**: 서비스 관리자는 초기 설정으로 준비한 권한으로 관리자 웹에 접속하고 보호된 운영 기능을 사용할 수 있어야 한다. 일반 회원·크루 관리자는 같은 접근 권한을 얻지 못해야 한다.

### 요구사항별 검증 연결

## Assumptions

- 선행 관계의 원본은 [개발 단위 목록](../README.md#선행-관계)이다. 실제 연동 선행: [001 개발 기반 구성](../001-development-foundation/spec.md), [003 앱 탐색과 공통 화면 부품](../003-app-shell/spec.md).
- 병렬 착수 전 필요한 계약: C01·C02·C03·C08·C09·C12. 설계 범위와 완료 조건은 [계약 설계 범위](../002-shared-contracts/contract-scope.md)를 따른다. 계약 확정 후 예제로 독립 개발할 수 있으나 실제 완료는 선행 기능과 연동해 확인한다.
- 기존 검증 연결: T01·T67·T75. T번호의 기대 결과는 [원본 검증표](../../docs/functional-spec.md#9-기능-완료-확인-시나리오)에 두고 복사하지 않는다.
- 개발자별 담당·단독 검사·전달과 합친 뒤 완료 기준은 [프론트·백엔드 작업 구분](../development-roles.md)을 따른다.
- [구현 계획](plan.md)·[32개 작업 목록](tasks.md)을 준비했고 계약3.0.0은 PR #60으로 병합했다. T001~T005 공통 기반의 구현/단독 검증은 [증거](../../docs/history/development/004-identity-foundation-verification.md)를 따른다. #51 모바일 인증·가입·이름 profile API의 [서버 단독 증거](../../docs/history/development/004-mobile-identity-api-verification.md)를 추가했다. #54 관리자 세션 소비·HTTPS 개발 도구의 [단독 증거](../../docs/history/development/004-admin-consumer-verification.md)를 추가했다. #57/T025의 [관리자 실제 HTTPS 연동 증거](../../docs/history/development/004-admin-auth-verification.md)를 추가했다. 앱 가입 흐름·사진·제공자/기기 연동은 후속이며004 전체 완료가 아니다.
