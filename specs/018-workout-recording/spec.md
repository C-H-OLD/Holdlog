- 담당 화면·영역: 02.13·기록 영역 표시줄·OS 알림. [02.13](../../docs/screen-design.md#screen-02-13) · [최신 시안 목록](../../docs/screens.md) · [전체 상태 번호](../../docs/screen-numbering.md).
- 기존 기능·정책 연결: F07·F16 확장. 상세 동작 원본: [기능 명세](../../docs/functional-spec.md)의 S12 · [운동 명세](../../docs/workout-recording-spec.md).
- 이 스펙은 개발 범위·기능 연결·수락 기준의 원본이다. 상세 제품 규칙·계산식·문구·화면 배치는 기존 원본에서만 수정한다.
- 경계: 시작 방식 선택과 새 시작 화면은 제외한다. 개인 기록 입력·상세를 새로 만들지 않는다.

## User Scenarios & Testing

### User Story 1 - 운동 중 빠른 기록 이용 (Priority: P1)

사용자 또는 개발 담당자는 아래 기능을 해당 원본의 조건으로 이용한다.

**Why this priority**: 이 개발 단위의 핵심 결과이며 후속 기능이 같은 자료를 사용할 기준이다.

**Independent Test**: 필요한 선행 자료를 공통 계약의 예제로 준비하고 요구사항별 검증 표의 상황과 원본 기대 결과를 비교한다. 예제 검사는 실제 서비스 연동 완료와 구분한다.

**Acceptance Scenarios**:

아래 [요구사항별 검증 연결](#요구사항별-검증-연결)의 각 행이 이 흐름의 수락 기준이다. 해당 상황에서 작업한 결과를 행에 지정한 원본 기대 결과와 비교한다.

### User Story 2 - 실패와 경계에서 자료 유지 (Priority: P1)

사용자는 실패·거절·동시 요청을 성공으로 오인하지 않고 기존 자료와 입력을 원본 기준으로 유지할 수 있다.

**Why this priority**: 정상 결과뿐 아니라 권한과 자료 보존이 기능 완료의 조건이다.

**Independent Test**: 각 FR의 해당 거절 조건과 아래 경계 사례를 준비해 저장 결과·조회 결과·화면 상태를 비교한다.

**Acceptance Scenarios**:

1. **Given** 작업 조건 또는 권한이 충족되지 않음, **When** 대상 작업을 요청함, **Then** 허용되지 않은 변경·조회가 발생하지 않고 기존 원본의 실패 결과를 따른다.
2. **Given** 저장 실패·중복 요청·동시 변경에 해당하는 상황, **When** 해당 작업을 재요청하거나 다시 조회함, **Then** 원본 기준의 자료 보존·중복 방지·충돌 결과를 확인할 수 있다.

### 대표 확인 사례

1. **Given** 암장을 선택한 운동이 진행 중임, **When** 화면 이동 후 기록 표시줄로 돌아가 운동을 종료함, **Then** 진행 값을 유지하고 개인 기록 하나를 저장하며 크루에 자동 연결하지 않는다.
2. **Given** 종료 없이 사용자가 앱을 강제로 종료함, **When** 이후 저장 결과를 확인함, **Then** 취소된 운동의 개인 기록이 생기지 않는다. OS 정리와 구분하는 실기기 검증도 별도로 필요하다.

대표 사례는 검증을 위한 짧은 요약이며 상세 규칙은 범위 표의 원본에서 관리한다.

### Edge Cases

- 종료 재요청·사용자 강제 종료·OS 정리·표시줄 겹침·기기 시계 변화·저장 실패를 구분한다.
- 공통 상태·실패·입력 보존은 [기능 명세2.1절](../../docs/functional-spec.md#21-상태와-입력)을 참조한다. 별도 상태 시안을 임의로 추가하지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 사용자는 선택 암장에서 진행 중 완등 개수를 조절하고 운동 종료 시 개인 기록을 한 번 저장할 수 있어야 한다.
- **FR-002**: 화면 이동·백그라운드에서는 운동을 유지하고 기록 영역의 공통 표시줄로 돌아갈 수 있어야 한다.
- **FR-003**: 진행 중 암장 변경·중복 운동 시작을 막고 종료 저장은 크루에 자동 연결하지 않아야 한다.
- **FR-004**: 사용자 강제 종료와 운영체제 정리를 구분해 취소·유지 결과를 검증하고 확정한 공통 운동 알림 정보를 제공해야 한다.

### 요구사항별 검증 연결

각 행의 상황을 확인하고 연결한 원본의 기대 결과를 따른다. 상세 규칙·계산식은 복사하지 않는다. T번호가 없는 항목은 해당 원본 절의 검증·완료 기준과 규정된 동작을 직접 검사한다. 프론트·백엔드 단독 검사와 실제 연동 검사에 같은 행을 사용하며 아직 실행한 결과는 없다.

| 요구사항 | 검사할 상황 | 기대 결과 원본·검증 항목 |
|---|---|---|
| FR-001 | 개수±1·0 하한·종료시 개인 기록 한번 저장·재요청 | [완료 확인 기준](../../docs/workout-recording-spec.md#완료-확인-기준) |
| FR-002 | 화면이동/백그라운드 유지·기록탭만 표시·표시줄 복귀·다른 UI 겹침 허용 | [기록 화면의 운동 중 표시줄](../../docs/workout-recording-spec.md#기록-화면의-운동-중-표시줄) · [완료 확인 기준](../../docs/workout-recording-spec.md#완료-확인-기준) |
| FR-003 | 진행중 암장변경/중복시작 차단·자동 크루연결 미생성 | [운동 기록 흐름](../../docs/workout-recording-spec.md#운동-기록-흐름) · [완료 확인 기준](../../docs/workout-recording-spec.md#완료-확인-기준) |
| FR-004 | 사용자 강제종료 취소·OS 정리 구분·Android/iOS 공통운동알림 | [공통 운동 알림](../../docs/workout-recording-spec.md#공통-운동-알림) · [완료 확인 기준](../../docs/workout-recording-spec.md#완료-확인-기준) |

### Key Entities

- 진행 중 운동·시작 시점·암장·완등 개수·종료 결과. 상세 필드와 형식은002 공통 계약 설계에서 정하며 여기에는 복사하지 않는다.

## Success Criteria

### Measurable Outcomes

- **SC-001**: FR-001~FR-004에 연결한 정상 수락 시나리오가 모두 원본의 기대 결과와 일치한다.
- **SC-002**: 각 FR의 해당 실패·거절 조건과 경계 사례에서 금지된 변경·조회·중복 생성이0건이다.
- **SC-003**: 요구사항별 검증 표에 연결한 원본 검증과 후속 설계에서 구체화한 추가 사례를 모두 통과하고 미수행 결과를 완료로 표시하지 않는다.
- **SC-004**: 담당 화면·부품을 최신 시안과 대조하고 검토 대기·미정 범위를 완료로 표시하지 않는다.

## Assumptions

- 선행 관계의 원본은 [개발 단위 목록](../README.md#선행-관계)이다. 실제 연동 선행: [003 앱 탐색과 공통 화면 부품](../003-app-shell/spec.md), [007 암장 검색·선택·지도·상세](../007-gym-discovery/spec.md), [009 개인 기록 작성·수정·상세](../009-personal-records/spec.md).
- 병렬 착수 전 필요한 계약: C04·C06·C12. 설계 범위와 완료 조건은 [계약 설계 범위](../002-shared-contracts/contract-scope.md)를 따른다. 계약 확정 후 예제로 독립 개발할 수 있으나 실제 완료는 선행 기능과 연동해 확인한다.
- 기존 검증 연결: [운동 완료 확인 기준](../../docs/workout-recording-spec.md#완료-확인-기준). T번호의 기대 결과는 [원본 검증표](../../docs/functional-spec.md#9-기능-완료-확인-시나리오)에 두고 복사하지 않는다.
- 개발자별 담당·단독 검사·전달과 합친 뒤 완료 기준은 [프론트·백엔드 작업 구분](../development-roles.md)을 따른다.
- 현재 기능의 결과는 범위 명세와 품질 확인이다. 공통 형식은 [002 계약 설계](../002-shared-contracts/contracts/README.md)에 작성했으며, 기능별 구현 계획·작업 목록·앱 코드·실제 연동/실행 검증은 아직 없다.
