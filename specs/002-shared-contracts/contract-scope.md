# 병렬 개발 전 공통 계약 설계 범위

작성일: 2026-10-06 · 상태: 범위와 API·데이터 계약 설계 작성. 서비스 구현·실제 소비자 연동 전.

공통 계약은 앱·서버·관리자 웹이 주고받을 값과 결과를 함께 정한 약속이다. 이 문서는 약속의 **범위·책임·원본 연결**을 관리한다. 실제 형식과 처리 의미는 [공통 계약](../../packages/contracts/README.md), 논리 저장 구조는 [데이터 모델](data-model.md)이 원본이다. 제품 규칙은 링크한 기존 명세가 원본이며 계산식·권한표를 여기에 다시 쓰지 않는다. [002 스펙](spec.md)의 후속 설계 범위다.

프론트·백엔드가 나눠 개발할 담당 범위와 계약 전달 절차는 [작업 구분 원본](../development-roles.md)을 따른다. 계약은 백엔드가 초안을 모으고 프론트가 소비 입력·결과·실패를 검토하며 양쪽 확인 후 확정한다. 사람 이름과 실제 변경 담당 배정은 후속 작업이다.

계약의 자료형과 입력 검증 정의는 한곳에서 관리하고 문서·예제·소비자가 같은 정의를 사용하도록 설계한다. 자동 생성이 필요한 자료도 원본과 생성 결과를 구분한다. 서버의 실제 권한 검사 코드는 서버에 두며 클라이언트 공통 자료형을 권한 근거로 사용하지 않는다. 공통 계약을 고칠 때 영향받는 기능 스펙·계획·예제도 함께 갱신한다.

## 후속 설계 순서

1. C01~C04에서 공통 표현·계정·역할·운영 데이터의 식별과 책임을 먼저 정한다.
2. C05~C07에서 일정·개인 기록·참석·연결의 관계와 함께 처리할 범위를 정한다. 논리 모델은 화면별 테이블로 나누지 않는다.
3. C08~C11에서 파일·조회·통계·추천·작업·이력·알림의 입력과 결과를 소비 기능 담당과 대조한다.
4. C12에서 로그인·초대·알림 진입·기기 상태를 맞춘다. 운동 시작 방식은 결정 전까지 분리한다.
5. 실제 계약 예제와 소비자 확인 방법을 정하고 영향받는 기능의 계획·작업을 작성한다. 코드 구현은 그 다음 단계다.

앱·서버·관리자 웹이 독립 작업을 시작하기 전에 해당 기능이 사용하는 C번호의 합의를 끝낸다. 나머지 계약이 미확정이면 영향 없는 기능만 진행할 수 있다. 공통 계약 설계는 기반 코드 설치를 기다릴 필요가 없지만 실제 소비자 검증에는001 기반이 필요하다.

## 계약 설계 완료 조건

- 각 C번호에 입력·성공 결과·허용/거절·실패·재시도·동시 변경·원본 정책 링크·변경 책임이 있다. 해당 없는 항목은 이유를 기록한다.
- 모든44개 화면과 현재 상태·공통 부품이 필요한 계약으로 연결되고 미정·검토 대기는 구분된다. 시안 숫자·브랜드·11색을 데이터 제한으로 쓰지 않는다.
- 같은 자료의 원본과 변경 책임이 하나이며 요청/응답/사건의 필드·단위·누락 표현이 서로 맞는다.
- 활성 연결·같은 일정 방문·가입 조합의 중복 제한과 하루 같은 지점 별개 방문 허용을 함께 확인한다.
- 함께 반영할 변경과 비동기 정리 작업을 나누고, 저장 후 작업 유실·중복·늦은 완료·권한 회수를 다루는 예제가 있다.
- 공통 예제가 정상·권한 거절·충돌·재시도·시간대·미입력/0·공개 회수·삭제 보존을 포함한다. 기능별 FR와 기존 T번호가 예제에 연결된다.
- 계약만 확정한 상태와 예제로 검사한 상태, 실제 서비스·기기에서 확인한 상태를 따로 기록한다.

설계 파일·형식 예제·정적 검토를 작성했다. 실제 생성 소비자 확인·백엔드 실행·프론트 연동·기기 검사를 통과한 것으로 표시하지 않는다. 단계별 확인은 [검증 안내](quickstart.md)를 따른다.

## 병렬 작업과 합친 뒤 확인

- 공통 계약·모델·DB 변경·루트 설정은 통합 담당 작업에서 관리한다. 기능 담당자는 자기 화면·서버 기능 영역을 맡으며 공통 파일 변경 요청을 먼저 모은다.
- 003은 공통 화면 부품을 담당한다. 007과016의03.02, 005와021의06.01, 004와021의05.02처럼 공유 화면은 주 화면 담당이 조립하고 보조 기능 담당은 계약 결과와 동작을 제공한다.
- 기능별 작업은 자기 스펙 경로와 `SPECIFY_FEATURE_DIRECTORY`, `SPECIFY_FEATURE_NO_PERSIST=1`을 사용한다. 새 스펙 생성과 공용 선택 파일 변경은 순차 수행한다. 자세한 방법은 [개발 흐름](../../docs/development-workflow.md#현재-기능-선택)을 따른다.
- 공통 예제로 단독 검사를 끝낸 뒤 [선행 관계](../README.md#선행-관계)의 실제 기능을 연결한다. 단독 검사만으로 연동 완료를 표시하지 않는다.
- 합친 뒤 로그인→가입→일정→실제 참석→개인 작성/연결→조회/통계→공개 변경→분리/삭제를 확인한다. 추천·알림·되돌리기·업로드 중 삭제·탈퇴도 같은 자료로 확인한다.
- 공지와 오픈소스 안내는 별도 흐름으로 확인하고 기본 로그인·초대 진입을 막지 않는지 대조한다. 운동은 확정된 본체 검사와 미정인 시작 진입을 나눠 기록한다.

## 이번 범위 밖

계약 필드·API 경로·세션·페이지·충돌 결과·공지 로그인 전 읽기·서비스 관리자 접속 방식은 [공통 계약](../../packages/contracts/README.md)에 설계했다. 실제 배포 주소·라이브러리 설치·서비스 구현은 후속 작업이다. 제품 명세를 새로 확정할 필요가 생기면 해당 원본을 갱신한다. 이미 정한 기술은 [기술 명세](../../docs/technical-spec.md)를 따른다.

운동 시작 방식은 [미결정 사항](../../docs/open-questions.md), 공지 시안 승인과 표시줄의 구현 적용 구분은 [화면 작업 목록](../../docs/screen-worklist.md), 계정·서버·기기 준비는 [준비 체크리스트](../../docs/setup-checklist.md)에만 둔다. 도메인·HTTPS·백업·장애 복구·배포 자동화·외부 저장소 업체 선택은 이번 공통 계약 설계의 착수 조건으로 추가하지 않는다.
