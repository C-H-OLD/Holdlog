# Feature Specification: 공통 계약 설계

**Feature Branch**: 미지정 (스펙 번호는 브랜치와 별개)

**Created**: 2026-10-06

**Status**: API·데이터·기기 계약 설계 작성 / 정적 검토·서비스 구현 전

**Input**: 기존 명세와 최신 시안을 개발 단위로 나누고 선행 관계 및 병렬 개발 전 계약 설계 범위를 정리한다.

## 범위와 원본

- 담당 화면·영역: —. [화면 설계](../../docs/screen-design.md) · [최신 시안 목록](../../docs/screens.md) · [전체 상태 번호](../../docs/screen-numbering.md).
- 기존 기능·정책 연결: 공통. 상세 동작 원본: [기능 명세](../../docs/functional-spec.md)의 2절·5절·6절·D01~D08·B01~B05.
- 이 스펙은 개발 범위·기능 연결·수락 기준의 원본이다. 상세 제품 규칙·계산식·문구·화면 배치는 기존 원본에서만 수정한다.
- 경계: 실제 API·데이터·기기 계약을 이번 설계에서 정한다. 기능 구현·기반 설치는 후속 작업이며 운동 시작 UI는 미정이다.

## User Scenarios & Testing

### User Story 1 - 공통 계약 설계 이용 (Priority: P1)

사용자 또는 개발 담당자는 아래 기능을 해당 원본의 조건으로 이용한다.

**Why this priority**: 이 개발 단위의 핵심 결과이며 후속 기능이 같은 자료를 사용할 기준이다.

**Independent Test**: 필요한 선행 자료를 공통 계약의 예제로 준비하고 요구사항별 검증 표의 상황과 원본 기대 결과를 비교한다. 예제 검사는 실제 서비스 연동 완료와 구분한다.

**Acceptance Scenarios**:

아래 [요구사항별 검증 연결](#요구사항별-검증-연결)의 각 행이 이 흐름의 수락 기준이다. 해당 상황에서 작업한 결과를 행에 지정한 원본 기대 결과와 비교한다.

### User Story 2 - 실패와 경계에서 자료 유지 (Priority: P1)

사용자는 실패·거절·동시 요청을 성공으로 오인하지 않고 기존 자료와 입력을 원본 기준으로 유지할 수 있다.

**Why this priority**: 정상 결과뿐 아니라 권한과 자료 보존이 기능 완료의 조건이다.

**Independent Test**: 각 FR의 해당 거절 조건과 아래 경계 사례를 준비해 저장 결과·조회 결과·화면 상태를 비교한다.

**Acceptance Scenarios**:

1. **Given** 작업 조건 또는 권한이 충족되지 않음, **When** 대상 작업을 요청함, **Then** 허용되지 않은 변경·조회가 발생하지 않고 기존 원본의 실패 결과를 따른다.
2. **Given** 저장 실패·중복 요청·동시 변경에 해당하는 상황, **When** 해당 작업을 재요청하거나 다시 조회함, **Then** 원본 기준의 자료 보존·중복 방지·충돌 결과를 확인할 수 있다.

### 대표 확인 사례

1. **Given** 앱·서버·관리자 담당자가 같은 연결 예제를 받음, **When** 공통 설계 원본으로 허용·거절 결과를 비교함, **Then** 세 담당자가 같은 결과를 읽을 수 있고 계약의 미확정 항목도 식별한다.
2. **Given** 운동 시작 방식이 미정임, **When** 계약의 설계 완료를 판단함, **Then** 운동 시작 진입을 확정 계약으로 표시하지 않고 영향 범위를 분리한다.

대표 사례는 검증을 위한 짧은 요약이며 상세 규칙은 범위 표의 원본에서 관리한다.

### Edge Cases

- 상충하는 원본이나 미정 범위가 발견되면 영향받는 계약만 미확정으로 남기고 임의의 제품 동작을 추가하지 않는다.
- 공통 상태·실패·입력 보존은 [기능 명세2.1절](../../docs/functional-spec.md#21-상태와-입력)을 참조한다. 별도 상태 시안을 임의로 추가하지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 개발자는 각 기능의 입력·결과·권한·실패·재요청 기준을 같은 원본에서 확인할 수 있어야 한다.
- **FR-002**: 설계 담당자는 계정·크루·일정·참석·개인 기록·연결·파일의 식별과 소유 관계를 정리하고 기능별 변경 책임을 구분해야 한다.
- **FR-003**: 기록 생성·연결·해제·삭제와 권한 회수의 함께 처리할 범위를 정하고 동시 변경의 허용·거절 결과를 합의해야 한다.
- **FR-004**: 시간대·기간·미입력·수치·중복 집계의 표현 기준을 정해 조회와 계산 결과가 서로 일치해야 한다.
- **FR-005**: 앱·서버·관리자 웹 담당자는 공통 예제로 정상·거절·충돌·재시도 결과를 비교할 수 있어야 한다.
- **FR-006**: 운동 시작 미정·공지 시안 승인·출시 설정을 구분하고 미정 범위를 확정 계약으로 표시하지 않아야 한다.

### 요구사항별 검증 연결

각 행의 상황을 확인하고 연결한 원본의 기대 결과를 따른다. 상세 규칙·계산식은 복사하지 않는다. T번호가 없는 항목은 해당 원본 절의 검증·완료 기준과 규정된 동작을 직접 검사한다. 프론트·백엔드 단독 검사와 실제 연동 검사에 같은 행을 사용하며 아직 실행한 결과는 없다.

## Success Criteria

### Measurable Outcomes

- **SC-001**: FR-001~FR-006에 연결한 정상 수락 시나리오가 모두 원본의 기대 결과와 일치한다.
- **SC-002**: 각 FR의 해당 실패·거절 조건과 경계 사례에서 금지된 변경·조회·중복 생성이0건이다.
- **SC-003**: 요구사항별 검증 표에 연결한 원본 검증과 후속 설계에서 구체화한 추가 사례를 모두 통과하고 미수행 결과를 완료로 표시하지 않는다.
- **SC-004**: 모든 개발 단위·담당 화면·기존 정책을 계약 범위에 연결하고 미정·검토 대기를 확정 계약으로 표시하지 않는다.

## Assumptions

- 설계 범위의 세부 목록은 [계약 설계 범위](contract-scope.md)다. 설계 착수는001 구현을 기다리지 않으며 아래001은 실제 소비자 실행 검증의 선행이다.
- 선행 관계의 원본은 [개발 단위 목록](../README.md#선행-관계)이다. 실제 연동 선행: [001 개발 기반 구성](../001-development-foundation/spec.md).
- 병렬 착수 전 필요한 계약: C01~C12. 설계 범위와 완료 조건은 [계약 설계 범위](../002-shared-contracts/contract-scope.md)를 따른다. 계약 확정 후 예제로 독립 개발할 수 있으나 실제 완료는 선행 기능과 연동해 확인한다.
- 기존 검증 연결: [요구사항별 검증 표](#요구사항별-검증-연결)에 지정한 원본 절과 완료 기준. T번호의 기대 결과는 [원본 검증표](../../docs/functional-spec.md#9-기능-완료-확인-시나리오)에 두고 복사하지 않는다.
- 개발자별 담당·단독 검사·전달과 합친 뒤 완료 기준은 [프론트·백엔드 작업 구분](../development-roles.md)을 따른다.
- 현재 결과는 [설계 계획](plan.md)·[데이터 모델](data-model.md)·[공통 계약](../../packages/contracts/README.md)·[검증 안내](quickstart.md) 작성과 정적 검토다. 기존001 기반 소비 증거를 재사용하고 [작업 목록](tasks.md)의 새 계약·소비 검사를 진행한다. 새 알림 계약의 실제 생성 소비와 제품 API/DB/기기 실행 검증은 아직 없다.

## 수신 목록 추가 계약

2026-10-07 확정된 수신 목록·읽음 요구사항은 C09·C12의 [남은 계약 범위](contracts/README.md#수신-알림-목록-추가에-따른-남은-계약)에 연결했다. 기존 계약 설계·생성 소비자 형식 검사는 이 추가 요구사항의 완료 증거가 아니다. 이 범위를 합의·설계한 뒤017 FR-005~006 구현을 시작한다.
